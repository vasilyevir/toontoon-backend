# Черновик изменений → потом пересборка документации

Рабочий документ **одного прохода**: сюда складываем новую логику (бэкенд + iOS),
здесь её ревьюим, и только после «принято» я одним заходом переписываю
документацию в обоих репозиториях. Веб не трогаем.

**Статус документа:** черновик, засеян фактами из кода. Ждёт описания новой логики.

---

## Как это устроено

**Жанры (не смешиваем):**

| Жанр | Отвечает на вопрос | Куда попадёт |
| --- | --- | --- |
| Reference | «как именно устроен контракт» | `openapi.json` (генерится из кода) + `docs/API.md` |
| Guide | «как поднять / настроить / зарелизить» | `docs/*.md` в своём репозитории |
| ADR | «почему решили так» | `docs/adr/NNN-название.md`, 1 страница |
| CHANGELOG | «что изменилось» | `CHANGELOG.md` в корне репозитория |
| MIGRATION | «что сделать клиенту, чтобы жить с новым сервером» | `arteki-ios-app/docs/MIGRATION.md` |
| Journal | снимок на дату, **не** источник правды | `docs/archive/` |

**Правила, которые удерживают доки от протухания:**

1. Один источник правды на факт. Дубль запрещён — вместо копии ссылка.
   Сейчас ~20 документов лежат в двух копиях, 6 из них уже разъехались.
2. Контракт API не пишется руками — дампится из кода; расхождение с живым
   сервером ловится проверкой, а не глазами. Сегодняшняя сверка нашла
   **16 эндпоинтов**, которых нет в `docs/openapi.json`.
3. PR, меняющий роут, в том же коммите правит `openapi.json` и `CHANGELOG.md`.
4. Всё, что является снимком состояния (аудит, worklog, отчёт), уезжает в
   `archive/` с датой в имени и шапкой «снимок на такое-то число».

**Шаблон записи об изменении:**

```
## CH-NN — Название
- Статус:        черновик | на ревью | принято | отклонено
- Затрагивает:   backend | iOS | оба
- Что меняется:  1–3 предложения по существу
- Зачем:         проблема, которую это решает
- Контракт API:  новые/изменённые ручки; breaking для клиента: да/нет
- Влияние на iOS: что придётся поменять в приложении
- Куда в доках:  reference / guide / ADR-NNN / CHANGELOG / MIGRATION
- Вопросы:       что ещё не решено
```

## Часть 1. Уже в коде, но нигде не описано

Это **не предложения**, а факты: код в `gen-backend` уже так работает
(незакоммиченные изменения + свежие коммиты), документация про это молчит.
На ревью нужно только подтвердить формулировку или поправить.

### CH-01 — `GET /api/app/bootstrap`: один запрос на холодный старт
- **Затрагивает:** оба
- **Что:** вместо пяти запросов (`auth/me` + `balance` + `tiles` + `tiles/featured`
  + `tiles/freeform-question`) приложение получает всё одним вызовом; плюс в ответе
  приходят история чатов и блок `config` с серверными переключателями фич
  (`image_teki_cost`, `video_teki_cost`, `push_enabled`, `google_enabled`, `apple_enabled`).
- **Зачем:** холодный старт и возможность гасить фичи на сервере без релиза приложения.
- **Контракт:** новая ручка, не breaking. Работает и без авторизации (`user`/`balance` = `null`).
- **iOS:** уже использует (`APIClient.bootstrap()`), кнопки Apple/Google скрываются по `config`.

### CH-02 — Вход по email и паролю вместо только magic-link
- **Затрагивает:** оба
- **Что:** `POST /api/auth/register`, `POST /api/auth/login`,
  `POST /api/auth/forgot-password`, `POST /api/auth/reset-password`,
  `GET /api/auth/magic-link/verify` (JSON-двойник веб-редиректа).
- **Зачем:** нативному клиенту неудобно ловить сессию из `Set-Cookie` за 302-редиректом.
- **Контракт:** 5 новых ручек, не breaking. Пароли — argon2.
- **Вопрос на ревью:** доставка писем не подключена — `forgot-password` в dev
  отдаёт токен прямо в ответе. Это временно или так и остаётся до продакшена?

### CH-03 — Сессия принимается и в `Authorization: Bearer`, и в cookie
- **Затрагивает:** оба
- **Что:** все точки входа возвращают `session_token` в JSON; сервер резолвит
  сессию из заголовка или из cookie `arteki-session`.
- **Зачем:** веб живёт на cookie, приложение — на Keychain + Bearer, ломать веб не хочется.
- **Куда в доках:** это решение, а не факт → **ADR**.

### CH-04 — Sign in with Apple
- **Затрагивает:** оба
- **Что:** `POST /api/auth/oauth/apple` — приложение получает `identity_token` от Apple,
  сервер проверяет **подпись** по публичному JWKS Apple и сверяет `aud` с нашим
  Bundle ID / Services ID (`APPLE_BUNDLE_ID`, `APPLE_SERVICE_ID`).
- **Зачем:** требование App Store при наличии стороннего входа.
- **Контракт:** новая ручка. Если audience не задан — `apple_enabled=false`, кнопка скрыта.
- **Куда в доках:** guide (настройка) + ADR (почему проверяем подпись сами, в отличие от Google/Boostyfi).

### CH-05 — Sign in with Google через браузерный флоу
- **Затрагивает:** оба
- **Что:** `GET /api/auth/google/login` + `/callback`; при `?platform=app` колбэк
  редиректит не на веб-фронт, а в `arteki://auth?...` — приложение забирает готовую сессию.
- **Статус в реальности:** `GOOGLE_CLIENT_ID` пустой → ручки отвечают 503, кнопка скрыта.
- **Вопрос на ревью:** заводим client id сейчас или переносим в отдельную задачу?

### CH-06 — История чатов живёт на сервере
- **Затрагивает:** оба
- **Что:** `GET/POST /api/chats`, `GET/PATCH/DELETE /api/chats/{id}`,
  `POST /api/chats/{id}/messages`. `/api/chat` и `/api/generate` сами пишут сообщения
  в тред, если им передали `chat_id`. Хранение — Redis.
- **Зачем:** до этого история существовала только в браузере — другой клиент,
  переустановка или второе устройство видели пустоту.
- **iOS:** уже читает; поле заголовка треда — `label` (проверено запросом, комментарий
  «request bodies unverified» в `Models.swift` пора снять).
- **Вопрос на ревью:** TTL истории в Redis и лимит сообщений в треде — не описаны.

### CH-07 — Первичная аналитика на своём сервере
- **Затрагивает:** оба
- **Что:** `POST /api/events` принимает батч анонимных событий (`anon_id` + список).
- **Куда в доках:** reference + guide; текущие ANALYTICS-* документы (три штуки,
  частично дубли) сводятся в один.

### CH-08 — Барьер приложения: app-key + подпись запроса
- **Затрагивает:** оба
- **Что:** middleware проверяет `X-Arteki-App-Key` и HMAC-подпись
  (`X-Arteki-Timestamp`, `X-Arteki-Signature`) по канонической строке
  `METHOD\nPATH\nTS\nsha256(body)`; исключения — `/api/uploads` и `/api/webhooks`.
- **Сейчас:** `APP_KEY_REQUIRED=false`, то есть выключено.
- **Куда в доках:** ADR (честно: секрет зашит в бинарнике, это «поднять планку», а не защита)
  + guide по включению.

### CH-09 — Текст на видео печёт Cloudinary
- **Затрагивает:** backend
- **Что:** `text_overlay` запекается в mp4 через Cloudinary; без `CLOUDINARY_CLOUD_NAME`
  видео отдаётся без текста. Модель с аудио (`seedance-2`) иногда думает дольше 10 минут,
  поэтому таймаут поллинга — 900 с.
- **Куда в доках:** reference (поля) + guide (переменные окружения).

### CH-10 — Кошелёк: Boostyfi и грант
- **Затрагивает:** backend
- **Что:** для пользователей Boostyfi как баланс показывается `grant_remaining`;
  обрабатывается `payment_expired` для долгих видео-задач; при недоступности Wallet API — мягкий 404.
- **Куда в доках:** BOOSTIFY-INTEGRATION переезжает в репозиторий бэкенда и чистится.

### CH-11 — Локальный запуск (сделано сегодня)
- **Затрагивает:** оба
- **Что:** `gen-backend/run-local.sh` поднимает новый бэкенд на **8020** (8000 занят
  gbr-backend, 8010 — aeo-analyzer), Redis — контейнер `arteki-redis`, боевой `.env`
  не трогается (перекрываем переменными окружения). iOS Debug смотрит на
  `http://localhost:8020`, пиннинг выключен, в ATS добавлен `NSAllowsLocalNetworking`.
- **Куда в доках:** guide «локальная разработка» в обоих репозиториях + CHANGELOG.

## Часть 2. Новая логика — сюда

Статус всей части: **черновик, разбираем по одной теме.** Референс интерфейса —
приложение Glam Agent (скриншот): чат-первый экран с прикреплением фото/видео,
таб-бар `Home / Shots / AI Chat / Feed`. У нас вместо Feed — История генераций.

### Узел, от которого зависит почти всё: аноним

Пункт 5 («логин только по прямому нажатию») — не экран, а смена модели данных.
Сейчас сервер знает только авторизованного пользователя: сессия → `user_id` →
кошелёк, генерации, чаты. Если генерировать можно **до** логина, то нужен
полноценный **гостевой субъект**: у него есть баланс, история, чаты — всё то же,
что у зарегистрированного, только без email. И нужна **склейка**: в момент входа
гостевые генерации, чаты и остаток баланса должны переехать в аккаунт, иначе
пользователь платит логином за потерю своей работы.

От этого решения зависят: CH-13 (история), CH-14 (переиспользование стиля),
CH-17 (монетизация — кому принадлежит покупка, сделанная гостем). Поэтому
разбираем его первым по существу, даже если по порядку он пятый.

**РЕШЕНО: гостевая сессия на сервере.** Гость — полноценный субъект, а не особый
случай. Альтернативы (хранить всё локально; аноним без истории) отклонены:
генерация всё равно происходит на сервере и её надо кому-то приписать, а «аноним
без истории» обнуляет темы 2 и 3 ровно для тех, ради кого делается тема 5.

Что из этого следует (черновик, уточняем по ходу):

- Пользователь получает третий вид `provider` — `guest`, наряду с `email`,
  `google`, `apple`, `boostify`. Всё, что привязано к `user_id` (кошелёк,
  генерации, чаты), работает без изменений.
- **Выдача сессии.** При первом запуске приложение получает анонимную сессию и
  кладёт в Keychain. Вариант: отдельная ручка `POST /api/auth/guest`; либо
  `bootstrap` заводит гостя сам, если запрос пришёл без сессии.
  → решить при описании контракта.
- **Склейка при входе.** Логин из-под гостя переносит генерации и чаты в аккаунт.
  Ручка вида `POST /api/auth/link` либо флаг в существующих точках входа.
  Слияние балансов зависит от CH-17 — **отложено до темы 6**, сейчас не решаем.
- **Что при входе в уже существующий аккаунт:** содержимое гостя доливается к
  тому, что уже есть (не заменяет). Гостевой `user_id` после переноса гасится.
- **TTL заброшенных гостей.** Гость, не сделавший ни одной генерации, не должен
  копиться в Redis вечно. Значение — открытый вопрос.
- **Границы гостя:** что ему нельзя. Как минимум — покупка (нужен аккаунт, иначе
  покупку не к чему привязать при переустановке). Полный список зависит от темы 6.
- **Риск, который надо принять осознанно:** гостевая сессия живёт в Keychain, то
  есть привязана к устройству. Потеря устройства = потеря истории. Это цена
  отложенного логина, и её стоит проговорить в тексте про апгрейд.

### CH-12 — Онбординг: квиз с подбором стилей
- **Затрагивает:** оба. **Источник:** макет Figma `Teki-App`, node `86-6536`.
- **Что это на самом деле.** Раньше в этой записи стояло «несколько экранов с
  рассказом о продукте, вопросов не задаём». Макет показывает другое: это
  **квиз**, который собирает пол и предпочтения по шести направлениям, а затем
  обещает персонализацию («We'll use this to personalize your AI styles and
  recommendations», «Personalizing your experience» на финальном лоадере).
  Прошлая формулировка отменена, ниже — фактический состав.

**Новые тексты отзывов (экран 12), пять карточек:**

1. *Amazing AI photos!* — I love the variety — realistic photos, cartoons,
   sketches, and new looks in seconds.

   art, or cartoons.

**Что это меняет в уже принятых решениях — три поправки, все приняты:**

1. **«Вопросов не задаём» отменено.** Онбординг собирает пол и шесть ответов
   (по одному на направление, ✕ или ♥). Это данные о пользователе, которых мы
   не планировали: их надо хранить, и они принадлежат гостю, то есть переезжают
   в аккаунт при склейке (CH-16).
2. **Экраны в сборке, ответы на сервере.** Вёрстка и картинки остаются зашитыми,
   а вот **ответы уходят на сервер** — без этого обещание «персонализируем
   подборку» невыполнимо, а лоадер «Personalizing your experience» врёт.
3. **Персонализация и ручная курация сосуществуют.** Ручной порядок (CH-14)
   остаётся базой выдачи, а направления, отмеченные ♥, **поднимаются наверх**.
   Так выполняются оба обещания: витрину собираем мы, а человек видит своё
   первым.

**Шесть направлений из онбординга = категории каталога.** AI Photo Studio,
Artistic Touch, Cartoon Me, Fantasy Mode, Pet Magic, Family Fun. Это прямо
задаёт верхний уровень каталога стилей (CH-14) и отменяет нынешние три категории
(Image / Postcard / Video). Миграция 29 плиток должна раскладываться именно
по этим шести.

**Что нужно на сервере:**

- профиль предпочтений: пол + отметки по шести направлениям, привязанные к
  `user_id` (в том числе гостевому);
- влияние предпочтений на выдачу главной и Shots;
- поле пола в профиле — с возможностью изменить позже (в CH-15 такого пункта нет).

**Технически удачный момент:** финальный лоадер «Preparing your AI workspace» —
это те несколько секунд, за которыми прячется реальная работа: создание гостевой
сессии, `bootstrap`, прогрев каталога. Экран уже нарисован, остаётся не тратить
его впустую на анимацию.

**Остаётся в силе:** показывается при первом запуске, **пропустить нельзя**,
флаг «пройден» хранится на устройстве, переустановка = онбординг заново,
обновление версии — нет. На каждый шаг нужны события аналитики: 13 шагов без
пропуска — это самое узкое место воронки, и без разметки мы не узнаем, где люди
отваливаются.

**Закрыто по итогам разбора макета:**

- **«Tap to preview» — просто кнопка «дальше»**, показывающая следующий шаблон.
  Ни загрузки фото, ни генерации на онбординге нет. Отсюда важное следствие:
  **онбординг не трогает ни камеру, ни галерею, ни токены** — доступ к
  фотографиям приложение впервые запрашивает уже внутри продукта, а не на входе.
  Это заметно снижает трение и снимает вопрос «за чей счёт превью».
- **Язык — английский**, весь интерфейс. Локализации на старте нет; пункт «язык»
  в настройках профиля (CH-15) до появления второго языка смысла не имеет —
  либо убираем его, либо оставляем задел.
- **Отзывы оставляем как в макете** — продуктовое решение. Оговорка остаётся
  в силе: заявленные цифры и отзывы должны выдерживать проверку на ревью
  App Store, ответственность за их достоверность на продуктовой стороне.

- **Экран отзывов остаётся на своём месте — показываем сразу.** Продуктовое
  решение: социальное доказательство важно именно до первой генерации.
  Мой довод про длину экрана в узком месте воронки снят с обсуждения; если
  цифры воронки покажут проблему, вернёмся с данными, а не с догадками.

**Открыто:**

- Сбор пола нужно задекларировать в App Privacy и описать в политике
  конфиденциальности (задача релизного чеклиста).

### CH-13 — Вкладка «История генераций» вместо Feed
- **Затрагивает:** оба
- **Что:** четвёртая вкладка таб-бара — история собственных генераций вместо ленты.
- **Решено:**
  - **плоская сетка, новое сверху**, разделители по дням; без вкладок и без
    группировки по чатам;
  - действия над элементом: **сохранить в галерею, поделиться, повторить/изменить,
    удалить**;
  - **храним бессрочно** — ничего не чистим по времени;
  - незавершённое видео **сразу появляется карточкой со статусом** и превращается
    в результат по готовности.
- **Что нужно на сервере:**
  1. **Пагинация курсором** в `GET /api/generations` (`cursor` + `limit`).
     Сейчас ручка отдаёт весь список одним куском — при бессрочном хранении это
     со временем станет мегабайтным ответом на каждое открытие вкладки.
  2. **Миниатюры для сетки.** У видео `thumbnail_url` уже есть, у изображений —
     нет: сетка будет тянуть полноразмерные картинки, по три в ряд. Нужно поле
     `thumbnail_url` и для изображений (Cloudinary уже подключён — можно взять
     трансформацию оттуда, отдельный ресайз не обязателен).
  3. **`DELETE /api/generations/{id}`** — ручки не существует. Вместе с записью
     решить судьбу файла на диске и **расшаренной ссылки**: после удаления
     `share_id` обязан перестать открываться, иначе «удалил» окажется ложью.
  4. **Хранить параметры запроса, а не только результат.** Сейчас в записи есть
     `prompt`, `tile_id`, `tile_label`, но нет `answers`, `style`, `photo_url` и
     `type`-специфики, с которыми запрос был отправлен. Без них «повторить/изменить»
     невозможно воспроизвести — воспроизведётся не то же самое.
  5. **Гость.** История работает по гостевой сессии и переезжает в аккаунт при входе.
- **Риск, который нужно закрыть до включения бессрочного хранения:** файлы лежат
  в локальной папке `uploads/` рядом с приложением, в k8s-скелете (`deploy/values.yaml`)
  тома нет вообще. Рестарт или переезд пода = потеря всех результатов, при том что
  пользователю мы обещали «храним всегда». Нужен либо постоянный том, либо внешнее
  хранилище (Cloudinary/S3/MinIO). **Это блокер темы 2, а не косметика.**
- **Принятое ограничение:** пуша о готовности видео не будет — на сервере только
  Web-Push (VAPID), для iOS он бесполезен, APNs не подключён. Значит статус
  обновляется, только пока приложение открыто; если пользователь вышел, он увидит
  результат при следующем заходе. Если это неприемлемо — APNs становится отдельной
  задачей (см. открытые вопросы).

### CH-14 — Главная с популярными стилями + Shots с ежедневными заготовками
- **Затрагивает:** оба
- **Что:** Home — популярные стили; Shots — ежедневные заготовки; готовый стиль
  можно переиспользовать.
- **Решено:**
  - **стиль — единственная сущность каталога, tiles уходят.** Стиль = пример
    результата + готовый промпт + параметры (тип, нужно ли фото, цена). Уточняющие
    вопросы, которые сейчас живут в `questions` у tile, переезжают в чат;
  - **порядок на главной задаём мы вручную**, никаких счётчиков популярности
    на старте: на текущем трафике автоматика была бы шумом, а витрина должна
    продавать продукт, а не отражать статистику;
  - **Shots — пул заготовок + детерминированная авторотация по дате.** Ежедневная
    ручная работа не нужна, набор на дату вычисляется из пула;
  - тап на стиль открывает **экран стиля с примерами** (что получится, цена,
    нужно ли фото), и уже с него — запуск;
  - **верхний уровень каталога задан онбордингом** — шесть направлений:
    **AI Photo Studio, Artistic Touch, Cartoon Me, Fantasy Mode, Pet Magic,
    Family Fun** (CH-12). Нынешние три категории (Image / Postcard / Video)
    отменяются: они описывали тип результата, а не то, зачем человек пришёл;
  - **выдача = ручной порядок + подъём отмеченного.** Базовый порядок задаём мы
    (`sort_order`), а направления, которым человек поставил ♥ на онбординге,
    поднимаются наверх. Тип результата (фото или видео) становится свойством
    стиля, а не разделом каталога.
- **⚠️ Миграции не будет: 29 плиток не ложатся на шесть направлений.**
  Я попробовал разложить фактический каталог — и он оказался про другой продукт.
  Состав сегодня: 15 открыток к праздникам (день рождения, свадьба, Пасха,
  День благодарения, выпускной…), 6 картинок «с нуля» (мультяшный персонаж,
  зверушка, птицы, рыбы, природа, еда), 8 видео. **Фото требуется ровно двум
  плиткам из 29** — `animate_photo` и `animate_pet`.

  Шесть направлений онбординга — все до единого про **своё фото**: «Turn your
  photo into a little masterpiece», «One tap to toon up your whole photo»,
  косплей, питомцы, семья. Ни одна существующая плитка этому не отвечает:
  `cartoon_character` рисует персонажа с нуля, а не превращает в мультяшку тебя.

  Совпадений при честной раскладке: Pet Magic ← `animate_pet`, Family Fun ←
  частично `animate_photo`. Остальные четыре направления — **пусто**. А 15
  открыток не попадают вообще ни в одно направление: для них в новом онбординге
  нет места.

  Вывод: это не переименование категорий, а **смена продукта**. Каталог под
  шесть направлений нужно создавать заново, а решение про судьбу открыток
  и поздравлений принимать отдельно (см. вопросы ниже).
- **Что нужно на сервере:**
  1. `GET /api/styles` — каталог с ручным порядком (поле сортировки + признак
     «на главной»), и карточка стиля: примеры, описание, цена, нужно ли фото.
  2. `GET /api/shots/daily` — набор на дату из пула, детерминированно
     (одинаковый ответ для всех при одном и том же дне).
  3. Запуск генерации по `style_id` вместо `tile_id`.
  4. Счётчик использований стиля стоит писать **с первого дня**, даже если сейчас
     он ни на что не влияет: когда захотим автосортировку, история уже будет.
- **Открыто:**
  - ротация Shots по UTC или по локальной дате устройства (UTC проще и
    воспроизводимее, локальная — честнее для пользователя);
  - доступны ли вчерашние наборы или день пропал безвозвратно;
  - `tiles` остаются как совместимость или удаляются сразу;
  - что показывать на главной гостю в самый первый заход (пусто, пока не решено).
- **Веб: решено — не учитываем.** Бэкенд дальше разрабатывается как mobile-first,
  слой совместимости для веб-фронта не делаем. Это значит, что `GET /api/tiles`,
  `/tiles/featured`, `/tiles/freeform-question` и приём `tile_id` в `POST /api/generate`
  исчезнут, и **веб-фронт перестанет работать** — принято сознательно, чинить его
  будем отдельной задачей, если и когда понадобится. Ниже по документу это же
  правило действует везде: контракт затачиваем под приложение.
- **Старые записи истории** ссылаются на `tile_id`/`tile_label`. Чтобы «повторить»
  из истории работало для них после миграции, нужна карта старый tile → новый стиль.

### CH-15 — Профиль как место для всех настроек
- **Затрагивает:** iOS (backend — по минимуму)
- **Решено, три блока:**
  1. **Аккаунт:** имя, email, аватар, вход (для гостя), выход, удаление аккаунта.
     Удаление обязательно — требование App Store, ручки `DELETE /api/auth/me`
     и `DELETE /api/auth/profile` уже есть.
- **Удаление аккаунта — это анонимизация, а не удаление строки.** Выяснилось
  при первой же проверке схемы: журнал операций ссылается на пользователя
  внешним ключом и физически не даёт его стереть — и это правильно, бухгалтерия
  не должна исчезать вместе с человеком. Поэтому удаление означает:
  снять email, имя и аватар, **физически стереть файлы** из хранилища
  (загрузки и результаты), проставить `deleted_at`, погасить сессии и
  расшаренные ссылки. Строки журнала и генераций остаются привязанными к
  идентификатору, который после этого никого не идентифицирует.
  Это удовлетворяет и требование App Store, и здравый смысл: человек исчезает,
  учёт остаётся.
  2. **Приватность и аналитика:** согласие на аналитику, правовые документы,
     очистка данных.
  3. **Приложение:** язык, тема, уведомления, качество генерации по умолчанию,
     поддержка, версия.
- **У гостя — тот же экран**, сверху добавляется блок «войдите, чтобы не потерять
  работы». Настройки доступны без аккаунта: логин ничего не разблокирует, он
  сохраняет.
- **Баланс в профиль не входит — он вынесен наверх, в постоянный элемент шапки.**
  Решено: остаток виден **сразу после онбординга**, наглядно, не требуя захода
  в профиль; тап по нему — вход в апгрейд. Это же и есть отдельная от профиля
  точка апгрейда из пункта 5.
- **Следствия вынесенного баланса:**
  - элемент шапки живёт на всех вкладках, где он осмыслен (как минимум главная,
    Shots, чат), и обязан иметь состояние для гостя — гость видит свой баланс так же;
  - баланс должен обновляться **сразу после генерации** без перезагрузки экрана:
    `POST /api/generate` уже возвращает новый баланс, но экраны каталога и истории
    тоже должны его подхватывать;
  - при двух корзинах (см. CH-17) надо решить, показываем ли одну общую цифру или
    разделяем «квота подписки» и «бесплатные»; **предлагаю одну цифру**, а разбивку
    показывать только на экране апгрейда — иначе главный экран превращается в бухгалтерию.
- **Сервер:** новые поля настроек (язык, тема, качество по умолчанию) — либо
  хранить на устройстве, либо расширять профиль. Раз настройки должны переживать
  переустановку и переезд с гостя на аккаунт, разумнее хранить на сервере;
  решаем при описании контракта.

### CH-16 — Логин только по прямому действию
- **Затрагивает:** оба
- **Решено:** экран входа больше не стоит перед использованием. Приложение
  открывается сразу в рабочем состоянии на гостевой сессии; вход происходит
  только по тапу на «апгрейд» или в профиле.
- **Следствия:**
  - логин перестаёт быть воротами и становится **сохранением работы** — это же
    надо говорить и в тексте на экране входа;
  - все экраны обязаны иметь состояние «гость»: главная, Shots, чат, история,
    профиль. Отдельно продумать пустую историю у нового пользователя;
  - магические ссылки и OAuth-редиректы должны возвращать пользователя туда,
    откуда он ушёл, а не на стартовый экран.
- **Открыто (уходит в тему 6):** что происходит, когда у гостя заканчивается
  бесплатный лимит — пейволл, требование аккаунта или и то и другое; можно ли
  гостю покупать.

### CH-17 — Монетизация: подписка App Store + токены
- **Затрагивает:** оба
- **Решено:**
  - основная модель — **автопродлеваемая подписка через App Store**, которая
    выдаёт **определённое количество токенов на неделю**;
  - **цена генерации зависит от стиля** — у каждого стиля своя стоимость в токенах;
  - **бесплатные пользователи** получают стартовый баланс и **ежедневные награды**;
  - **гость может купить подписку без регистрации**;
  - **Boostyfi полностью убирается из мобильного приложения** — ни оплаты, ни входа.
- **Конкретные цифры (размер подписки, недельная квота, цены стилей, стартовый
  баланс, размер ежедневной награды) будут позже** — контракт описываем так, чтобы
  они были данными на сервере, а не константами в коде приложения.
- **Что нужно на сервере:**
  1. **Проверка подписки на стороне сервера.** Клиенту верить нельзя: статус
     подтверждается через App Store Server API, плюс серверные уведомления
     (App Store Server Notifications v2) для продлений, отмен, возвратов и
     grace period. Подписка опознаётся по `originalTransactionId` и связывается
     с `user_id`.
  2. **Начисление квоты по неделям — решено, и правило разное для двух типов:**
     - **подписчик:** недельная квота **сгорает** и раз в неделю
       **устанавливается в максимум тарифа** (не прибавляется). Тариф на 850 →
       в начале периода ровно 850, сколько бы ни осталось;
     - **бесплатный:** стартовый баланс и ежедневные награды **не сгорают**,
       копятся.
     Из этого следует **две отдельные корзины** в кошельке, а не одно число:
     сгораемая квота подписки и несгораемый бесплатный остаток. Иначе еженедельный
     сброс до 850 либо съест накопленное бесплатно, либо не сможет опуститься до
     нужного значения.
  2а. **Порядок списания — решено:** сначала тратится **сгораемая квота подписки**,
     и только когда она исчерпана — несгораемый бесплатный остаток. Так бесплатные
     токены не пропадают вместе с недельным сбросом.
  2б. **Потолок бесплатной корзины — решено: он есть.** Конкретное значение
     определяется позже, вместе с ценовой политикой. Без потолка неактивный
     пользователь копил бы награды месяцами и разряжал их залпом в самые дорогие
     стили. В контракте это параметр сервера, а не константа в приложении.
     Отдельно надо решить (позже, вместе со значением): что происходит с
     ежедневной наградой при достигнутом потолке — не начисляется вовсе или
     начисляется до кромки.
  2в. **Якорь недельного цикла — решено:** сброс каждые **7 дней от даты покупки**,
     независимо от событий App Store. Если тариф длиннее недели, внутри периода
     будет несколько сбросов. Отдельный якорь нужен потому, что иначе «неделя»
     плавала бы вслед за продлениями и спорила с ними.
  2б. **Неоплата и grace period.** Если платёж не прошёл, квота на новый период
     не выдаётся. Надо решить, что видит пользователь: остаётся с нулём, с
     бесплатной корзиной или получает временный доступ на время grace period.
  3. **Ежедневные награды:** серверный учёт «когда забирал в последний раз»,
     защита от накрутки переводом часов на устройстве (считаем по серверному
     времени), решение про серии/стрики.
  4. **Стоимость в стиле.** Цена переезжает из `image_teki_cost` / `video_teki_cost`
     (сейчас две глобальные константы) в поле стиля. Клиент показывает цену
     **до** запуска.
  5. **Покупка гостём.** Подписка привязана к Apple ID, баланс — к гостевому
     `user_id` на сервере. При входе оба переезжают в аккаунт (см. узел про гостя).
  6. **Восстановление покупок** — обязательная кнопка по правилам App Store.
- **Риск, который надо описать честно:** восстановление подписки ≠ восстановление
  баланса. Подписка вернётся по Apple ID на любом устройстве, а накопленные токены
  гостя привязаны к сессии в Keychain — при потере устройства без входа они
  пропадут. Это второй аргумент в пользу входа, и его стоит проговорить в тексте.
- **Конфликтные случаи, которые надо описать до реализации:** один Apple ID —
  два наших аккаунта; один аккаунт — два Apple ID; покупка гостём, который потом
  входит в аккаунт, где подписка уже есть.
- **Судьба Boostyfi на сервере:** из приложения он уходит, но код остаётся
  (OAuth, Wallet API, вебхуки, логика `grant_remaining` из CH-10). Раз бэкенд
  теперь mobile-first, это мёртвый код. Удалять ли его — **отдельное решение**,
  сознательно не смешиваем с этой темой.
- **Осталось из CH-15:** где пользователь видит остаток токенов, если в профиле
  блока баланса нет.

### CH-18 — Библиотека медиа: свои загрузки как источник референсов
- **Затрагивает:** оба
- **Статус:** модель закладываем сейчас, экран делаем позже.
- **Что:** загруженные пользователем фотографии **хранятся бессрочно и привязаны
  к аккаунту**. Выбирая референс, человек попадает не в системную галерею
  телефона, а в **галерею приложения**, где лежат его прошлые загрузки — и туда
  же вперемешку показываются его сгенерированные работы, если он захочет
  переиспользовать результат как референс.
- **Почему это надо заложить сразу, а не потом:** если референс — временный файл,
  он и хранится как временный, и в базе его нет. Тогда позже придётся не
  «добавить экран», а перекладывать хранилище. Поэтому в схеме сразу появляется
  единая таблица `media_assets` (загрузки и результаты в одной сущности) —
  см. [ARCHITECTURE-DRAFT.md](ARCHITECTURE-DRAFT.md).
- **Что из этого получается бесплатно:** переиспользование результата как
  референса становится не отдельной механикой, а выбором строки другого вида;
  дедупликация повторных загрузок; удаление аккаунта чистит всё одним проходом.
- **Приватность:** бессрочное хранение лиц требует срезать EXIF при загрузке
  (в фотографиях с телефона лежат GPS-координаты съёмки), приватного бакета и
  физического удаления объектов при удалении аккаунта.
- **Открыто:** лимит на объём библиотеки; можно ли удалять отдельную загрузку,
  если на ней основаны прошлые генерации (предлагаю можно — генерация уже
  сохранила результат); сортировка и фильтры в галерее.

### CH-19 — Генерация из своего фото: сегодня её нет
- **Затрагивает:** backend в первую очередь. **Статус:** блокер продукта, не документации.
- **Что обнаружилось.** Онбординг обещает превращение **своей** фотографии
  в стиль. Пайплайн генерации этого не делает и не может: загруженное фото
  уходит в vision-модель, которая **описывает его текстом**
  (`content_gen.analyze_photo` → Pollinations, таймаут 7 с), описание
  подмешивается в промпт, и дальше вызывается
  `POST /v1/images/generations` — text-to-image **с нуля**.
- **Что это значит на практике.** Человек загружает своё лицо, а получает
  портрет постороннего, похожего лишь описанием: «женщина, тёмные волосы, улыбка».
  Ни image-to-image, ни редактирования, ни сохранения личности в изображениях
  нет — ни одного вызова `images/edits`, никакого IP-Adapter, никакого identity-lock.
- **Уточнение: в видео фото уже используется по-настоящему.** Для плиток
  `animate_photo` и `animate_pet` `video_gen` передаёт фотографию в kie.ai как
  `first_frame_url` — это настоящий image-to-video, и сходство там держится
  ровно настолько, насколько его держит Seedance. То есть **обвязка уже
  существует**: файл кладётся в хранилище, получает публичный адрес и уходит
  провайдеру. Не хватает такой же ветки в генерации изображений.
- **Ещё одна деталь, которая станет проблемой.** `analyze_photo` при таймауте
  (7 секунд) молча возвращает пустую строку, и генерация продолжается **без
  учёта фотографии вообще**. Сегодня это мягкая деградация, а в фото-первом
  продукте — «твоё фото проигнорировали и списали токены». Должно стать ошибкой
  с возвратом, а не тихим пропуском.
- **Почему это критично именно сейчас.** Все шесть направлений онбординга и
  вся идея «переиспользовать стиль на своём фото» (CH-14) стоят на сходстве.
  Без него онбординг обещает то, чего продукт не умеет, и первая же генерация
  это обнаружит — причём у человека, который прошёл 13 обязательных экранов.
- **Что для этого нужно:** генерация с сохранением личности. Варианты, каждый
  со своей ценой и качеством: `images/edits` у gpt-image-1; модели уровня
  Flux Kontext / Seedream / nano-banana (часть доступна через уже подключённый
  kie.ai, где сейчас берётся видео); связка SDXL + InstantID/IP-Adapter на
  своих мощностях. Выбор — отдельная проработка с тестами на реальных лицах,
  потому что «похоже» здесь решает всё.
- **Смежное:** `media_assets` и бессрочное хранение фото (CH-18) обретают
  дополнительный смысл — референс перестаёт быть одноразовым описанием и
  становится входом модели.

### CH-20 — Один чат вместо списка тредов
- **Затрагивает:** оба. **Отменяет часть CH-06.**
- **Решено:** у пользователя **один непрерывный чат**, а не набор бесед.
  Предыдущая история сохраняется и доступна прокруткой вверх.
- **Что из продукта исчезает:** боковая шторка со списком бесед, создание,
  переименование и удаление треда, выбор «в какой чат писать». Референс
  (Glam Agent) устроен так же: единственный чат и кнопка **Clear** в шапке.
- **Почему это скорее упрощение, чем потеря:** у нас уже есть отдельная вкладка
  **История** со всеми работами (CH-13). Треды решали задачу «найти свою прошлую
  работу», и эту задачу история решает лучше — сеткой, а не списком названий.
  Оставлять оба механизма значит держать два ответа на один вопрос.
- **Что меняется на сервере:**
  - `chats` схлопывается: одна строка на пользователя (или таблица уходит
    вовсе, а `chat_messages` живут по `user_id`). Ручки
    `POST /api/chats`, `PATCH /api/chats/{id}`, `DELETE /api/chats/{id}`,
    `GET /api/chats` — не нужны; остаётся получение ленты сообщений
    с пагинацией и добавление;
  - `chat_id` в `generations` остаётся: связь «сообщение → генерация» нужна,
    чтобы результат отображался в ленте на своём месте;
  - `bootstrap` больше не отдаёт список бесед — вместо него хвост ленты;
  - в приложении исчезает `chats()` / `createChat()` / `deleteChat()`
    из `APIClient`, вместе с недоверенными телами запросов, о которых
    предупреждал комментарий в `Models.swift`.
- **Что появляется взамен:**
  - **пагинация ленты назад** — единственный чат растёт бесконечно, загружать
    его целиком нельзя;
  - **окно контекста для модели** — вся лента в запрос к LLM не поместится
    и будет дорожать с каждым сообщением. Нужно правило, сколько истории
    уходит в модель;
  - **склейка гостя**: сообщения гостя и аккаунта сливаются в одну ленту
    по времени — конфликтов нет, поскольку тред один.
- **Clear — начинает новый контекст, ничего не удаляя.** Модель забывает
  предыдущий разговор, человек — нет: лента остаётся и прокручивается вверх.
  Это ровно та задача, ради которой кнопку нажимают («хочу про другое»), и она
  не спорит с решением хранить историю.
  Следствия: в ленте нужен **видимый разделитель** «здесь начался новый
  разговор» — иначе непонятно, почему ассистент вдруг «забыл»; на сервере это
  отметка времени сброса, а не удаление строк.
- **В модель уходят последние ~20 сообщений**, не старше отметки последнего
  Clear. Цена запроса не растёт с возрастом ленты — у активного пользователя
  иначе чат дорожал бы бесконечно. Число вынести в настройку сервера, а не
  зашивать в код: подобрать его можно будет только на живых разговорах.
- **Открытых вопросов по чату не осталось.**

### CH-21 — Два режима ввода и расширяемая модель генерации
- **Затрагивает:** оба. **Развивает CH-19.**
- **Сейчас делаем немного:** оставляем текущие возможности (текст → изображение,
  текст → видео, фото → видео для двух сценариев) и добавляем **фото →
  изображение**. Больше в первую версию не берём.
- **Но закладываем модель, в которую позже входят** анимация фото из любого
  стиля, удаление или замена объекта по выделенной области, апскейл, замена фона
  и новые провайдеры — **без переписывания пайплайна**.

**Три понятия, на которых всё держится.**

1. **Операция** — что вообще делаем: `text_to_image`, `image_to_image`,
   `image_to_video`, `inpaint` (правка выделенной области), `outpaint`,
   `upscale`. Это закрытый список, который растёт по мере надобности.
2. **Стиль** — что получит пользователь: обещание, пример, цена. Стиль
   **объявляет** нужную операцию и то, что требуется на входе.
3. **Провайдер** — чем сделано: OpenAI, kie.ai, что угодно дальше. Провайдер
   **объявляет**, какие операции умеет.

Связь односторонняя: стиль не знает про провайдера, провайдер не знает про стиль,
их сводит операция. Отсюда и берётся расширяемость: **добавить модель — значит
написать адаптер и включить строку в реестре**, не трогая роутеры, каталог
и приложение.

**Что описывает стиль (`input_spec`).** Вместо нынешнего булева `needs_photo` —
описание входов: нужен ли промпт, нужно ли исходное изображение, нужна ли маска,
какие параметры (соотношение сторон, длительность). Это даёт главное для
приложения: **экран запуска собирается по описанию**, а не пишется заново под
каждую новую операцию. Появится инпейнт — у стиля в `input_spec` окажется маска,
и тот же экран покажет выделение области.

**Реестр провайдеров.** Адаптер живёт в коде, а строка реестра — в базе:
включён или нет, приоритет, поддерживаемые операции, ограничения (размер входа,
формат), ориентиры по цене и времени. Тогда переключение модели, аварийный откат
на запасную и A/B двух моделей — это данные, а не релиз.

**Маршрутизация:** стиль → операция → первый включённый провайдер по приоритету,
с фоллбеком на следующий. Ровно так уже работает откат gpt-image-1 → dall-e-3,
только зашитый в одну функцию — вытаскиваем его наружу.

**Всё делаем асинхронным сразу.** Сегодня картинки синхронные (клиент ждёт до
300 с), видео — фоновая задача с поллингом. Это два разных контракта на одно и
то же действие. Инпейнт и тяжёлые модели будут ближе к видео, поэтому единая
модель задачи нужна с самого начала: `POST /generate` всегда возвращает job,
клиент всегда опрашивает статус, а быстрые операции просто завершаются к первому
опросу. Иначе первый же медленный провайдер сломает контракт, который к тому
моменту будет в сторе.

**Что сохраняем в записи генерации:** операцию, провайдера и модель, версию
входов, ссылки на исходное медиа и маску. Без этого не работает ни «повторить»
(CH-13), ни разбор жалоб, ни сравнение моделей между собой.

**Маска — обычный медиа-объект** (`media_assets.kind = 'mask'`), со своим
хранением и приватностью. Отдельной сущности не заводим.

**Возможности объявляются клиенту** в `bootstrap`: приложение показывает только
то, что сервер сегодня умеет. Инпейнт появится на сервере — кнопка появится
в приложении без релиза, если экран уже умеет собираться по `input_spec`.

- **Что это стоит сейчас:** примерно один рефакторинг генерации вместо трёх
  будущих. Мы всё равно переписываем пайплайн ради фото (CH-19) — разумно сразу
  сделать это правильной формы.
- **Открыто:** ничего блокирующего; конкретный список операций первой версии —
  `text_to_image`, `image_to_image`, `image_to_video`.

## Открытые вопросы к ревью

**Блокеры — без них соответствующую тему нельзя начинать:**

1. ~~**Хранилище файлов** (CH-13)~~ — **закрыт решением** в
   [ARCHITECTURE-DRAFT.md](ARCHITECTURE-DRAFT.md): объектное S3-совместимое
   хранилище за абстракцией, приватный бакет с подписанными ссылками, CDN
   подключается позже. Осталось выбрать площадку (MinIO в кластере или R2) —
   это уже не блокирует описание.

   Там же приняты в работу два дефекта, найденных при проектировании:
   история обрезается до 200 записей (`_MAX_HISTORY`), и каталог `/uploads`
   отдаётся публично без авторизации вместе с загруженными фото людей.

2. **Генерация из своего фото** (CH-19) — **блокер №1, решение принято:
   продукт строится вокруг фото.** Подбор модели с сохранением личности и
   проверка на реальных лицах идут раньше остального: от того, какая модель
   выбрана, зависят промпты стилей, цена генерации и время ответа — то есть
   весь каталог и вся экономика. Пока модель не выбрана, наполнять каталог
   бессмысленно.

3. **Старый каталог уходит в архив, новый пишется с нуля.** 15 открыток,
   6 картинок и 8 видео из `tiles_data.py` не мигрируют. Шесть направлений
   наполняются новыми фото-стилями под выбранную модель. Открытки и
   видеопоздравления — отдельный продуктовый разговор, к которому вернёмся
   при желании; смешивать их с фото-первым продуктом не будем.

**Закрыто по умолчанию** — решения приняты с обоснованием, возражай, если иначе:

4. **Ротация Shots — по UTC.** Одинаковый набор для всех и воспроизводимо
   в тестах; локальная дата дала бы разным людям разные «сегодня» и сделала бы
   отладку гаданием. **Вчерашние наборы доступны 7 дней назад** — пропустить
   день не значит потерять его навсегда, а хранение стоит одной строки в запросе.
5. ~~Карта «старый `tile_id` → новый стиль»~~ — **не нужна.** Старые данные
   не переносим (чистый старт), а каталог создаётся заново: переводить нечего.
6. **TTL гостевых сессий: 30 дней для гостя без единой генерации**, гость
   с генерациями не удаляется никогда. Чистим пустышек, но не трогаем того,
   у кого есть работы: он может вернуться через полгода, и потерять его историю
   ради экономии строки в базе — плохой размен.
7. **Пуш о готовности видео: APNs на старте не делаем.** Статус обновляется,
   пока приложение открыто, и досчитывается при следующем заходе. Ограничение
   принято сознательно и записано в CH-13; APNs — отдельная задача, когда
   появится ощутимая доля длинных видео.
9. **Google client id — откладываем.** Кнопка скрыта серверным флагом
   `google_enabled`, продукт от этого не страдает: Apple, email и гостевой режим
   покрывают вход. Включается заведением credentials, без единой правки кода.
10. **Код Boostyfi удаляем.** Из мобилы он уходит (CH-17), веб не учитываем,
    а при переезде на Postgres и переписывании кошелька на две корзины его ветка
    в `wallet.py` всё равно перестаёт существовать. Держать мёртвый OAuth,
    Wallet API и вебхуки «на всякий случай» — это поддерживать то, что никто
    не проверяет.
11. **История чатов — бессрочно, как и генерации.** В Postgres нет причины
    ставить TTL: это те же данные пользователя. Лимита сообщений в треде нет,
    длинные треды решаются пагинацией.
12. **Лимит на объём библиотеки медиа на старте не ставим**, но пишем `bytes`
    у каждого объекта и смотрим на реальные цифры. Вводить потолок вслепую —
    значит угадывать; поле заложено, решение станет запросом, а не миграцией.
13. **Пункт «язык» из профиля убираем** до появления второго языка. Настройка,
    которая ничего не меняет, — это ложь интерфейса; вернём вместе с локализацией.
14. **Удаление отдельной загрузки разрешено**, даже если на ней основаны прошлые
    генерации: результат хранится отдельным объектом, у генерации просто
    обнуляется `source_media_id`. Запрещать удаление своей фотографии ради
    целостности ссылки — неверный приоритет, когда речь о лицах.
15. **Галерея медиа:** сортировка по дате, три фильтра — всё / загрузки / мои
    работы. Поиска нет.
16. **На главной поиска нет**, показываем 8 стилей и «показать ещё». Витрина
    должна продавать, а поиск нужен там, где человек знает, что ищет — на старте
    он не знает.
17. **Сбор пола декларируем в App Privacy** и описываем в политике — это задача
    релизного чеклиста, а не открытый вопрос.
18. **Конфликты подписки** (один Apple ID — два аккаунта и наоборот) — отложено
    вместе с темой монетизации.
19. **Аналитика — PostHog, своё не храним.** SDK уже в приложении, продуктовая
    воронка считается там. Ручка `/api/events` остаётся техническим каналом
    (ошибки API и подобное) и **не пишет в основную базу**: таблицы `events`
    в схеме нет. Поток мелких записей, которые никто не читает поштучно, не должен
    жить рядом с деньгами и историей.
20. **Доставка писем — оставляем dev-режим до релиза.** Токен сброса
    возвращается прямо в ответе API, это осознанно и удобно на время разработки.
    **Жёсткий пункт релизного чеклиста:** перед публикацией либо подключается
