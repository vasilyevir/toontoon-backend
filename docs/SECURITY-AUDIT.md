### Три находки, которых в аудите не было

Все три нашлись при починке, и ни одна — чтением кода.

**`POST /api/chat` без сессии доходил до модели.** Ветка «сессии нет» всё равно
уходила в языковую модель: за неё платил кто угодно, даже гостя заводить не
требовалось. Найдено при развешивании счётчиков.

**Разбор `X-Forwarded-For` у uvicorn включён по умолчанию** и переписывает
`request.client.host`, если сосед по сокету входит в `--forwarded-allow-ips`
(по умолчанию 127.0.0.1). Починка TT-008 из-за этого не работала: адрес сокета,
на который она опирается, сам приходил из заголовка. Поймано пробой — счётчик
завёлся на подставленном адресе при `TRUSTED_PROXY_COUNT=0`. Лечится
`--no-proxy-headers`; тест читает `Dockerfile` и `run-local.sh`, потому что
живёт эта настройка не в коде.

**`hmac.compare_digest` на строках с не-ASCII бросает `TypeError`.** Ключ и
подпись приложения приходят заголовками, которые пишет клиент: уронить проверку
пятисоткой вместо честного 401 мог кто угодно одной строкой, на каждом `/api/*`.
Ровно эту ошибку уже чинили в `/health/pulse` («в байтах, а не в строках»), а
здесь она осталась. Нашлась случайно — константы в новом тесте оказались
русскими.

### Оставлено намеренно

**Окно повтора подписи — 300 секунд, без разового номера.** Повторить
перехваченный подписанный запрос может только тот, кто его перехватил, — а
вместе с ним у него и токен сессии из того же запроса, то есть он и так может
слать свои собственные. Разовый номер стоил бы обращения к Redis на каждый
запрос и не закрывал бы ничего сверх этого.

## 🟠 High

### TT-001 — Гонка в списании: пять кадров по цене одного

**Файл:** `app/db/repositories/wallet.py:238` (`spend`)
**OWASP/CWE:** A04:2021 / CWE-362 (TOCTOU), CWE-841
**Риск фикса:** 🟥 средний — трогаем деньги

Баланс читается, проверяется и записывается **абсолютным значением**, посчитанным в
Python, без блокировки строки:

```python
wallet = await ensure(session, user_id)                       # SELECT без FOR UPDATE
if wallet.sub_balance + wallet.free_balance < cost:
    raise InsufficientFunds(...)
wallet.free_balance -= remaining                              # UPDATE ... SET free_balance = <из питона>
```

Два одновременных запроса читают одно и то же число и оба записывают результат своего
вычитания. Postgres на READ COMMITTED второй UPDATE не отменит — он применит то
значение, которое уже посчитано по устаревшему чтению.

**Доказано.** Пять одновременных `spend()` на балансе 15 при цене 15, прогретый пул
соединений, никаких искусственных задержек:

```
зпр0..зпр4: СПИСАНО ×5
кадров выдано: 5    заплачено: 15 монет
баланс: free=0      сумма журнала: −60
→ ЖУРНАЛ НЕ СХОДИТСЯ С БАЛАНСОМ
```

Первый прогон дал одно списание из пяти — и это была ловушка: соединения к базе
создавались по одному, четверо ждали не результата, а подключения. На прогретом пуле,
то есть на любом работающем сервере, проходят все пять.

Ломается заодно то, что обещано в шапке того же файла: «баланс всегда можно пересчитать
суммой журнала». После гонки журнал показывает −60, баланс — 0.

**Вектор:** послать N одновременных `POST /api/generate`. Ограничитель `gen:{user_id}`
(30/час) считает через Redis `INCR` — он атомарен и потолок держит, но внутри потолка
кадров выдаётся столько, сколько запросов ушло разом.

**Рекомендация:** брать строку кошелька под блокировку и вычитать относительно, а не
абсолютом. Плюс сетка снизу, которая не зависит от кода:

```sql
ALTER TABLE wallet_balances
  ADD CONSTRAINT free_not_negative CHECK (free_balance >= 0),
  ADD CONSTRAINT sub_not_negative  CHECK (sub_balance  >= 0);
```

```python
wallet = await session.get(m.WalletBalance, user_id, with_for_update=True)
```

Проверка в базе важнее блокировки в коде: блокировку однажды забудут добавить в новом
пути, а CHECK стоит под всеми.

**Трудозатраты:** S (одна строка + миграция). **Тест:** прогон из `scratchpad/race_probe3.py`
переносится в `tests/test_wallet.py` почти как есть.

### TT-002 — Повторно предъявленный чек воскрешает возвращённую подписку

**Файл:** `app/db/repositories/subscriptions.py:29` (`_fields`), `:60` (`refresh`)
**Путь:** `POST /api/auth/transaction` → `identity_service.by_transaction` → `refresh`
**OWASP/CWE:** A04:2021 / CWE-841 (нарушение порядка состояний)

`_fields()` ставит `"status": "active"` жёстко, по факту наличия чека:

```python
def _fields(payload: dict) -> dict:
    return {
        "product_id": ...,
        "status": "active",                                   # ← безусловно
        "current_period_end": _moment(payload.get("expiresDate")),
        ...
    }
```

`refresh()` раскладывает это по строке подписки. А `refresh()` зовётся каждый раз, когда
человек предъявляет свой чек — в том числе после того, как вебхук Apple поставил
`refunded` или `expired`.

Чек при этом настоящий, свой собственный, подписанный Apple. Отозвать сохранённую строку
JWS нельзя: она у человека на руках навсегда.

**Доказано:**

```
1. покупка привязана     → status='active' environment='sandbox'
   срок действия истёк   → 2025-08-12
2. пришёл REFUND         → status='refunded'   подписка действует? нет
3. чек предъявлен снова  → status='active'     подписка действует? ДА
```

Внутри те же две беды:

* **Возврат отменяется.** Деньги вернули — подписка снова действует.
* **Срок никто не смотрит.** `current_period_end` пишется в базу и **не читается нигде
  во всём коде** (проверено `grep`: единственные упоминания — запись и определение
  колонки). `active_for_user` фильтрует только по `status == "active"`. Просроченный чек
  за 2025 год даёт действующую подписку в 2026-м, и `ensure_subscription_quota` начинает
  пополнять недельную квоту.

**Рекомендация:** состояние выводить, а не назначать. `_fields` не должен трогать
`status` вовсе; отдельная функция считает его из `expiresDate` и из того, что уже стоит:
`refunded` и `revoked` — состояния конечные, чек их не переигрывает. И `active_for_user`
обязана смотреть на `current_period_end > now()`.

**Трудозатраты:** M. **Риск фикса:** 🟥 средний — можно случайно отключить платящих,
нужен прогон на копии базы.

### TT-003 — Чек из песочницы принимается как настоящая покупка

**Файл:** `app/services/app_store.py:305` (`verify_transaction`)
**OWASP/CWE:** A04:2021 / CWE-863

Проверка подписи здесь сделана хорошо — корень Apple прибит побайтно, цепочка проходится
звено за звеном, даты, алгоритм ES256, bundleId, вложенная транзакция перепроверяется.
Но чеки песочницы подписаны **тем же корнем Apple**, и отличает их единственное поле:
`environment`.

Оно читается и кладётся в базу (`subscriptions.py:34`), и на этом всё: ни
`verify_transaction`, ни `by_transaction`, ни `active_for_user` его не смотрят. В прогоне
выше подписка с `environment='sandbox'` стала действующей наравне с купленной.

Покупка в песочнице бесплатна. Её делает любой сборкой из TestFlight или пересобранным
IPA — то есть подписка выписывается себе даром.

**Рекомендация:** в `verify_transaction` отвергать всё, кроме `production`, если не
включён `debug`. Одна ветка рядом с `_check_bundle`, который уже стоит там же и делает
ровно это для чужих приложений.

**Трудозатраты:** S.

### TT-004 — Гостей заводить можно без счёта, и каждому дают монеты

**Файл:** `app/routers/auth.py:66` (`POST /api/auth/guest`)
**OWASP/CWE:** API4:2023 (Unrestricted Resource Consumption) / CWE-770

Ручка без аутентификации и **без единого ограничителя**. Каждый вызов заводит
пользователя и начисляет `signup_toontoon_balance` = 30 монет.

**Доказано на живом сервере:** 20 запросов подряд с одного адреса →

```
создано гостей: 20    отклонено: 0
кошельков: 20, монет на них всего: 600
```

600 монет при цене кадра 15 — это 40 генераций. Из двадцати HTTP-запросов. Ограничитель
`gen:{user_id}` (30/час) здесь бесполезен: у каждого гостя свой счётчик.

Двадцать тысяч запросов — 40 000 генераций. По себестоимости кадра $0.04–0.16 это
**$1 600–6 400** нашими деньгами, добываемые скриптом на десять строк.

**Рекомендация:** ограничитель на `/api/auth/guest` по адресу (скажем, 5/час) —
но это полумера, пока адрес берётся из заголовка (см. TT-008). Настоящий замок —
`DeviceCheck` / App Attest от Apple: гость заводится только по подтверждению, что
запрос пришёл из нашего приложения на настоящем устройстве. Ключ приложения
(`APP_KEY_REQUIRED`) написан и лежит выключенным — он закроет большую часть этого
и стоит одного флага.

**Трудозатраты:** S на ограничитель, M на App Attest.
**Связано:** TT-005 (усиливают друг друга), TT-008.

### TT-006 — Pillow 11.0.0 разбирает присланные байты сорока одним декодером

**Файлы:** `app/routers/generate.py:59` (список типов), `app/storage/images.py:66`
**OWASP/CWE:** A06:2021 / CWE-1035, CWE-434

Две половины, и опасны они вместе.

**Первая: список разрешённых типов ничего не ограничивает.** Роутер проверяет
`file.content_type` — заголовок, который пишет клиент. Дальше байты уходят в
`Image.open()`, а он выбирает декодер по содержимому, а не по заголовку.

**Доказано:**

```
роутер пускает: image/gif, image/jpeg, image/png, image/webp

TIFF объявлен как image/png → Pillow опознал TIFF и РАЗОБРАЛ
BMP  объявлен как image/png → Pillow опознал BMP  и РАЗОБРАЛ
TGA, PPM, SGI, DDS, ICNS    → то же самое

сколько декодеров Pillow готов пустить в дело: 41
```

**Вторая: в этих сорока одном декодере 17 известных дыр.** `pip-audit` по
`requirements.txt`:

```
pillow  11.0.0  17 уязвимостей  чинит 12.3.0
```

Достижимые нашим путём — те, что срабатывают при чтении:

| ID | Что | Достижимо |
|----|-----|-----------|
| PYSEC-2026-2249 | PSD: запись за границей буфера | да, объявив image/png |
| PYSEC-2026-2252 | PSD: порча памяти | да |
| PYSEC-2026-3496 | JPEG2000: переполнение по тайлам | да |
| PYSEC-2026-3493 | `raw`-кодек: чтение за границей | да |
| PYSEC-2026-3451 | координатные API: запись за границей кучи | да |
| PYSEC-2026-2250 | FITS: несдержанная распаковка GZIP | да |
| PCF/BDF/FontFile (5 шт.) | шрифты | нет, шрифты не грузим |
| PYSEC-2026-2257 | WindowsViewer через cmd.exe | нет, Linux |

Порог входа — один неаутентифицированный `POST /api/auth/guest` (см. TT-004).

**Рекомендация:** обе половины.

```python
# 1. поднять: Pillow==12.3.0
# 2. app/storage/images.py — назвать декодеры поимённо
Image.open(io.BytesIO(data), formats=["PNG", "JPEG", "WEBP", "GIF"])
```

Второе нужно **даже после** обновления: оно убирает из досягаемости тридцать семь
декодеров, про которые мы ничего не знаем, вместо того чтобы чинить дыры по одной.
`Image.MAX_IMAGE_PIXELS = 64_000_000` там уже стоит и работает — это хорошо и остаётся.

### TT-007 — PyJWT 2.10.1: обход списка алгоритмов на пути проверки Apple-токена

**Файл:** `app/services/apple_oauth.py:61`
**OWASP/CWE:** A02:2021 / CWE-347

```
pyjwt  2.10.1  7 уязвимостей  чинит 2.13.0
```

Две из них — ровно про то, что делает эта строка:

* **PYSEC-2026-176** (2.9.0–2.12.1) — «обход списка разрешённых алгоритмов на стороне

* **PYSEC-2026-179** (<2.13.0) — путаница между асимметричным и симметричным ключом при

обязаны проверить сами». Проверяет её библиотека с дырой в проверке.

константа в коде, не пользовательский ввод.

**Рекомендация:** `PyJWT[crypto]==2.13.0`. Одна строка в `requirements.txt`.

**Трудозатраты:** S.

### TT-008 — Ограничитель по IP обходится заголовком

**Файлы:** `app/routers/auth.py:170` (`_client_ip`), `app/routers/events.py:41`
**OWASP/CWE:** A07:2021 / CWE-290 — чеклист называет это прямо: AUTH-6.5

```python
def _client_ip(request: Request) -> str:
    return (request.headers.get("x-real-ip")
            or (request.headers.get("x-forwarded-for", "").split(",")[0].strip())
            or (request.client.host if request.client else "unknown"))
```

Оба заголовка пишет кто угодно. **Доказано на живом сервере** (14 запросов на
`/api/auth/forgot-password`, потолок 10/час с адреса):

```
один адрес                        → прошло 10, отклонено 4
адрес подменяется каждый запрос   → прошло 14, отклонено 0
```

Задеты все ограничители по адресу: `register` (10/час), `forgot` (10/час),
`transaction` (30/час), `reset` (20/900с), `events` (120/мин).

**Честная оговорка.** За ingress-nginx `X-Real-IP` перезаписывается прокси, и первая
ветка становится доверенной — то есть в проде эта конкретная дыра закрыта. Но: (1)
ingress ещё не включён (`values.yaml`, `ingress.enabled: false`), сейчас сервис доступен
напрямую; (2) запасная ветка берёт `X-Forwarded-For[0]` — **левый** элемент, а прокси
дописывает справа, так что там всегда стоит то, что прислал клиент; (3) нигде не
закреплено, что прокси обязан перезаписывать заголовок.

Ограничители по почте (`login:email` 8/900с, `forgot:email` 3/900с) не обходятся — перебор
одного аккаунта закрыт.

**Рекомендация:** доверять заголовку только от известного прокси — брать
`X-Forwarded-For[-N]` по числу своих прокси, а не `[0]`, и только когда сокет пришёл из
доверенной сети. Иначе — `request.client.host`.

## Что проверено и оказалось в порядке

Это половина работы, и её стоит записать — чтобы в следующий раз не проверять заново.

**Инъекции (05).** Сырого SQL нет нигде: чистый SQLAlchemy ORM, ни одной `text()` с
подстановкой, ни одного f-string в запросе. `subprocess` один
(`video_gen.py:136`) — `create_subprocess_exec` со списком аргументов, без оболочки,
имена файлов генерируем сами. Ни `eval`, ни `pickle`, ни `yaml.load`.

**IDOR (02).** Проверены **все** ручки, принимающие идентификатор: медиа, генерации,
профили, идеи, вложения чата, закладки, примеры стилей. Владелец сверяется везде, и
везде отдаётся `404`, а не `403` — существование чужого объекта не подтверждается.
`_chosen_references` в `profiles.py` берёт снимки без проверки, но оба вызывающих
проверяют их строкой выше. Массового присвоения нет: тела — явные Pydantic-модели,
`setattr` только по своему списку полей.

**SSRF (11).** `photo_url` разбирается регуляркой по `/api/media/{id}` и всё
остальное игнорирует (`generate.py:975`) — внешний адрес не запрашивается, а
отбрасывается. Это ровно тот случай, где обычно и находят SSRF.

**Подпись App Store (14).** Сделано лучше, чем в большинстве проектов: корень Apple
прибит **побайтно** (не «доверенный центр», а этот сертификат), цепочка проходится
звено за звеном, даты у каждого, алгоритм ES256 закреплён, вложенная транзакция
уведомления перепроверяется отдельно. Защита от повтора уведомлений — первичный ключ по
`notification_uuid`. Претензии к этому файлу (TT-003, TT-015) — про поля тела, не про
криптографию.

**Пароли и токены (01, 07).** Argon2id. Единая ошибка входа, не выдающая существование
почты. Ограничитель по почте, который не обходится. `secrets.token_urlsafe(32)` для
magic-link и сброса, оба одноразовые.

**Секреты (04).** `.env` не в git и никогда там не был (`git log --all -- .env` пуст).
`.env.example` чист — проверен построчно, реальных значений нет. По всем отслеживаемым
файлам ни одного совпадения с шаблонами ключей.

**Кошелёк, кроме гонки (17).** Начисления идемпотентны по ключу с уникальным индексом,
и гонка на них ловится `IntegrityError` — это сделано верно. Перенос баланса гостя —
один раз на аккаунт, ключом по цели, что закрывает «набрал наград гостем, вошёл,
повторил». Ежедневная награда считается по серверной дате.

**Загрузка (12).** EXIF срезается пересохранением (в телефонных снимках лежат
координаты) — и на это есть тест. Потолок в 64 мегапикселя от бомбы сжатия стоит.
Дедупликация по хешу.

**Приватность медиа (24).** Публичное монтирование `/uploads` убрано; всё идёт через
`/api/media` с проверкой владельца и `Cache-Control: private`. Удаление аккаунта стирает
файлы из хранилища, а не только обезличивает строку.

**Прод-настройки (10, 19).** Чарт закрепляет `DEBUG=false`,
`SESSION_COOKIE_SECURE=true`, `ACCEPT_STOREKIT_TEST_ROOT=false`, `APPLE_BUNDLE_ID`.
Кука `httponly`. Ingress выключен до выдачи домена — и это правильно.

**Обработка ошибок (23).** Своих обработчиков исключений нет, наружу уходит стандартное
`{"detail": "Internal Server Error"}` без трассировки. В логи секреты не пишутся —
проверено поиском по всем вызовам логгера.
