# Архитектура под новые механики — черновик

Парный документ к [CHANGES-DRAFT.md](CHANGES-DRAFT.md): там — что меняем и почему,
здесь — на чём это стоит. Пока черновик под ревью; на этапе пересборки документации
разъезжается по двум репозиториям (серверная часть остаётся здесь, раздел про iOS
уезжает в `arteki-ios-app/docs/ARCHITECTURE.md`).

Всё, что ниже, исходит из принятых решений: mobile-first, гость — полноценный
субъект, история бессрочная, стили вместо tiles, подписка App Store с двумя
корзинами токенов.

---

## 0. Три находки, которые определяют архитектуру

Это не мнения, а состояние кода на сегодня.

**1. Вся система живёт в Redis. SQL нет вообще.** В Redis лежат пользователи
(`user:email:*`, `user:apple:*`), сессии, генерации (`generation:{id}` + список
`user:generations:{uid}`), чаты, шеринг, токены магических ссылок и **баланс**
(поле `teki_balance` прямо на объекте пользователя). Ни одной таблицы, ни одной
транзакции, ни одного журнала операций.

Для сессий и кэша это нормально. Для денег — нет. Как только появляется подписка
за реальные деньги, «баланс — это поле в JSON-объекте в Redis» означает: любой
сбой при записи молча съедает или дарит токены, восстановить историю списаний
невозможно (её нет), а расследовать жалобу «я платил, куда делось» нечем.

**2. История уже обрезается до 200 записей.** В `generations_service.py`
`_MAX_HISTORY = 200` и `ltrim` при каждой записи. Мы договорились «храним
бессрочно» — сейчас код делает противоположное и молча выбрасывает старое.

**3. Файлы пользователей лежат в публичном каталоге.** `main.py` монтирует
`/uploads` как статику **без какой-либо авторизации**, и туда же складываются
референсные фото, которые загружает пользователь, — то есть лица живых людей.
Любой, кто получил ссылку (а она уходит в шеринг, в логи, в CDN, в историю
браузера), открывает файл. Отдельно: `app_key_exempt_prefixes` явно выводит
`/api/uploads` из-под проверки подписи.

Это уже не про новые механики, а про приватность сегодняшних пользователей —
и переезд на нормальное хранилище закрывает заодно и это.

**4. Генерация не умеет того, что обещает онбординг.** Загруженное фото
не попадает в модель как изображение: `content_gen.analyze_photo` отправляет его
в vision, получает **текстовое описание**, подмешивает в промпт и вызывает
`POST /v1/images/generations` — text-to-image с нуля. Сходства с человеком
на фото нет и быть не может. Все шесть направлений онбординга и
переиспользование стиля «на своём фото» стоят ровно на этом сходстве.

Это блокер продукта, а не архитектуры, и он крупнее трёх предыдущих: те про то,
как мы храним данные, а этот — про то, умеет ли продукт делать обещанное.
Подробности и варианты — CH-19 в [CHANGES-DRAFT.md](CHANGES-DRAFT.md).

**Статус: находка 1 закрыта решением о PostgreSQL, находки 2 и 3 приняты
в работу как дефекты, находка 4 требует продуктового решения.**

- `_MAX_HISTORY = 200` и `ltrim` убираются вместе с переездом истории в Postgres —
  до этого момента «бессрочно» технически не выполнимо, и обещать его в интерфейсе
  нельзя.
- Публичный `/uploads` закрывается вместе с переездом на объектное хранилище:
  бакет приватный, наружу — только подписанные ссылки с коротким сроком.
  До переезда это остаётся известной дырой, а не забытой.

## 1. Где что хранится

| Данные | Сейчас | Предлагается | Почему |
| --- | --- | --- | --- |
| Пользователи, привязки провайдеров | Redis | **PostgreSQL** | связи, уникальность email/apple_id, аудит |
| Сессии (в т.ч. гостевые) | Redis | **Redis** | короткоживущие, TTL — родная механика |
| Кошелёк: балансы и журнал | Redis (поле у юзера) | **PostgreSQL** | деньги: транзакции, идемпотентность, разбор жалоб |
| Подписки App Store | — | **PostgreSQL** | состояние, продления, уникальность транзакции |
| Генерации (метаданные) | Redis список, 200 шт | **PostgreSQL** | бессрочно, пагинация, фильтры, мягкое удаление |
| Чаты и сообщения | Redis | **PostgreSQL** | те же причины |
| Каталог стилей и Shots | код (`tiles_data.py`, 464 строки) | **PostgreSQL** + кэш в Redis | курация без релиза, счётчики, ротация |
| Результаты и загруженные фото | локальная папка `uploads/` | **S3-совместимое хранилище**, приватный бакет | долговечность, объём, приватность |
| Rate limits, локи, кэш, дедуп вебхуков | Redis | **Redis** | ровно то, для чего он нужен |
| Аналитика событий | Redis/лог | **PostHog**, в своей базе не храним | поток мелких записей не должен жить рядом с деньгами |

Смысл разделения: **Redis остаётся, но перестаёт быть системой учёта.** Он
становится тем, чем и должен быть, — быстрым слоем, потеря которого неприятна,
но не фатальна. Всё, что нельзя потерять, уезжает в Postgres.

Инфраструктура это уже предполагает: в `deploy/values.yaml` есть `initSchema`
с примером Alembic и упоминание `DATABASE_URL` в секретах — просто ещё не
заполнено.

## 2. Схема данных

**Решено: PostgreSQL добавляем.** Стек — SQLAlchemy 2.0 (async) + asyncpg,
миграции Alembic (`initSchema` в чарте уже под это заготовлен). Роутеры не ходят
в БД напрямую: между ними и таблицами слой репозиториев в `app/db/`, иначе
запросы расползутся по обработчикам, как сейчас расползся Redis.

Ниже — состав таблиц. Типы указаны для предметности, точный DDL родится в
миграции.

### Личность

```sql
users
  id                 uuid pk
  kind               text  not null   -- 'guest' | 'registered'
  email              citext unique     -- null у гостя
  password_hash      text              -- argon2, null у OAuth и гостя
  name               text
  avatar_key         text              -- ключ объекта в хранилище, не URL
  created_at         timestamptz not null
  last_seen_at       timestamptz       -- для чистки заброшенных гостей
  deleted_at         timestamptz
  merged_into_user_id uuid references users(id)   -- след склейки гостя

auth_identities
  user_id            uuid references users(id) on delete cascade
  provider           text  -- 'email' | 'apple' | 'google'
  external_id        text
  created_at         timestamptz
  unique (provider, external_id)

user_preferences                -- ответы онбординга (CH-12)
  user_id            uuid pk references users(id) on delete cascade
  gender             text       -- 'female' | 'male' | 'other'
  liked_categories   text[]     -- направления, отмеченные ♥
  disliked_categories text[]    -- отмеченные ✕ — тоже сигнал, не мусор
  onboarding_version text       -- какой набор вопросов человек проходил
  completed_at       timestamptz
```

`user_preferences` заводится **у гостя** — онбординг проходят до логина — и
переезжает в аккаунт при склейке вместе со всем остальным. `onboarding_version`
нужен потому, что набор направлений со временем изменится, и без него старые
ответы будет невозможно интерпретировать.

Гость — строка в `users` с `kind='guest'`, а не параллельный механизм: всё, что
работает для зарегистрированного, работает и для него без ветвлений. Склейка
не удаляет гостя, а проставляет `merged_into_user_id` — так остаётся след, если
понадобится разбирать спор.

### Кошелёк — две корзины и журнал

```sql
wallet_balances
  user_id            uuid pk references users(id) on delete cascade
  free_balance       integer not null default 0   -- несгораемая корзина
  sub_balance        integer not null default 0   -- сгораемая квота подписки
  sub_period_start   timestamptz                  -- якорь: 7 дней от покупки
  sub_period_end     timestamptz
  free_cap           integer                      -- потолок бесплатной корзины
  last_reward_date   date                         -- ежедневная награда
  reward_streak      integer not null default 0
  updated_at         timestamptz not null

wallet_ledger              -- append-only, только INSERT
  id                 bigserial pk
  user_id            uuid not null references users(id)
  bucket             text not null      -- 'free' | 'sub'
  delta              integer not null   -- + начисление, − списание
  reason             text not null      -- signup | daily_reward | sub_grant |
                                        -- sub_reset | generation | refund | merge
  ref_id             text               -- generation_id, transaction_id, …
  idempotency_key    text unique        -- защита от повторов
  balance_after      integer not null   -- для быстрой сверки
  created_at         timestamptz not null
```

`daily_rewards` отдельной таблицей не делаю — две колонки в `wallet_balances`
закрывают ту же задачу без лишнего join'а на каждом запросе.

Правило, которое делает деньги надёжными: **запись в журнал и изменение баланса
происходят в одной транзакции**, баланс всегда можно пересчитать суммой журнала,
а повтор операции с тем же `idempotency_key` не делает ничего.

Порядок списания (решение CH-17) — сначала `sub_balance`, затем `free_balance`;
одна генерация может дать две строки журнала, если списание пересекло границу.

### Подписка

```sql
subscriptions
  id                      uuid pk
  user_id                 uuid not null references users(id)
  original_transaction_id text not null unique   -- ключ подписки у Apple
  product_id              text not null
  status                  text not null  -- active | grace | expired | refunded
  current_period_start    timestamptz
  current_period_end      timestamptz
  environment             text           -- sandbox | production
  last_notification_at    timestamptz
  raw_payload             jsonb

appstore_notifications         -- журнал уведомлений, он же дедуп
  notification_uuid  text pk
  type               text
  subtype            text
  received_at        timestamptz
  payload            jsonb
```

`original_transaction_id` уникален глобально — именно это не даёт одной покупке
кормить два аккаунта, а `notification_uuid` как первичный ключ делает повторную
доставку уведомления безвредной без единой строки специальной логики.

### Контент

```sql
styles
  id               text pk            -- человекочитаемый: 'cartoon_character'
  title            text not null
  description      text
  operation        text not null      -- что делаем: text_to_image |
                                      -- image_to_image | image_to_video |
                                      -- inpaint | outpaint | upscale (CH-21)
  input_spec       jsonb not null     -- что нужно на входе: промпт, исходное
                                      -- изображение, маска, параметры.
                                      -- Экран запуска собирается ПО НЕМУ
  category         text not null      -- одно из шести направлений онбординга:
                                      -- ai_photo_studio | artistic_touch |
                                      -- cartoon_me | fantasy_mode |
                                      -- pet_magic | family_fun
  type             text not null      -- image | video: свойство стиля,
                                      -- а НЕ раздел каталога
  needs_photo      boolean not null default false
  cost             integer not null   -- цена в токенах, зависит от стиля
  prompt_template  jsonb not null     -- то, что сейчас зашито в tiles_data.py
  examples         jsonb              -- ключи примеров в хранилище
  sort_order       integer not null default 0   -- ручная курация
  is_home          boolean not null default false
  is_shot          boolean not null default false
  is_active        boolean not null default true
  usage_count      bigint not null default 0    -- пишем с первого дня
  created_at       timestamptz

shots_schedule                        -- необязательное ручное переопределение
  date             date pk            -- дня, который иначе считается автоматом
  style_ids        text[] not null

media_assets                      -- единая библиотека медиа пользователя
  id               uuid pk
  user_id          uuid not null references users(id)
  kind             text not null     -- 'upload' | 'generation' | 'mask'
                                     -- маска для inpaint — обычный объект,
                                     -- отдельной сущности не заводим (CH-21)
  storage_key      text not null     -- ключ объекта, НЕ url
  thumb_key        text
  mime             text
  bytes            bigint
  width            integer
  height           integer
  content_hash     text              -- sha256: повторная загрузка не плодит копии
  created_at       timestamptz not null
  deleted_at       timestamptz
  unique (user_id, content_hash) where kind = 'upload' and deleted_at is null

generation_providers          -- реестр моделей: адаптер в коде, строка здесь
  id               text pk            -- 'openai_images' | 'kie_seedance' | …
  operations       text[] not null    -- какие операции умеет
  model            text not null      -- конкретная модель провайдера
  priority         integer not null   -- порядок выбора и фоллбека
  is_enabled       boolean not null default true
  limits           jsonb              -- размер входа, форматы, длительность
  cost_hint        jsonb              -- ориентир по цене и времени

generations
  id                uuid pk
  user_id           uuid not null references users(id)
  style_id          text references styles(id)
  operation         text not null      -- что выполняли (CH-21)
  provider_id       text references generation_providers(id)
  provider_model    text               -- снимок: чем сделано на самом деле
  status            text not null      -- queued | running | done | failed
  prompt            text
  request_params    jsonb not null     -- ответы и параметры: то, чего сейчас нет
  source_media_id   uuid references media_assets(id)  -- какой референс взяли
  mask_media_id     uuid references media_assets(id)  -- для inpaint
  result_media_id   uuid references media_assets(id)  -- что получилось
  cost              integer not null default 0
  share_id          text unique        -- null, пока не расшарено
  created_at        timestamptz not null
  deleted_at        timestamptz        -- мягкое удаление

chat_messages          -- ОДИН непрерывный чат на пользователя (CH-20)
  id               bigserial pk
  user_id          uuid not null references users(id) on delete cascade
  role             text not null    -- 'user' | 'assistant'
  content          text
  generation_id    uuid references generations(id)  -- если сообщение породило работу
  created_at       timestamptz not null

users.chat_context_started_at   timestamptz
```

Таблицы `chats` нет: беседа одна, заводить сущность ради строки на пользователя
незачем. По той же причине из `generations` убран `chat_id` — связь
«сообщение → работа» держит `chat_messages.generation_id`, и держит её в одном
месте вместо двух.

Индексы, без которых экран истории начнёт тормозить на первой же тысяче записей:

```sql
create index on generations (user_id, created_at desc) where deleted_at is null;
create index on generations (user_id, type, created_at desc) where deleted_at is null;
create index on chat_messages (chat_id, created_at);
create index on wallet_ledger (user_id, created_at desc);
```

**Мягкое удаление осознанно:** «удалить из истории» не должно стирать строку, на
которую ссылается журнал списаний. Пользователь перестаёт видеть работу, файл из
хранилища удаляется, `share_id` гасится — а бухгалтерия остаётся целой.

### Библиотека медиа — почему отдельная таблица

Решение «референсные фото хранятся бессрочно и привязаны к аккаунту» превращает
загруженный файл из временного мусора в **сущность с собственной жизнью**.
А будущий выбор референса «из галереи приложения, где вперемешку загрузки и
сгенерированное» означает, что оба вида медиа должны лежать **в одной таблице**,
иначе экран выбора придётся собирать из двух запросов с ручной сортировкой по дате.

Отсюда `media_assets`: одна строка на файл, `kind` различает происхождение,
генерация ссылается на свой результат и на взятый референс. Что это даёт даром:

- **экран выбора референса** — один запрос с фильтром и пагинацией;
- **переиспользование результата как референса** — не новая механика, а просто
  выбор строки с `kind='generation'`;
- **дедупликация по `content_hash`** — одна и та же фотография, загруженная
  трижды, занимает место один раз;
- **удаление аккаунта** очищает файлы одним проходом по таблице, а не поиском
  по трём разным местам;
- **счётчик занятого места** на пользователя — сумма `bytes`, если понадобятся
  лимиты.

**Приватность, которая теперь обязательна.** Бессрочное хранение лиц поднимает
цену ошибки, поэтому в момент загрузки:

1. **Срезаем EXIF.** Фотографии с телефона несут GPS-координаты места съёмки.
   Хранить их годами рядом с лицом — ровно то, чего делать нельзя, и обходится
   это одной строкой при обработке.
2. **Приватный бакет и подписанные ссылки** — без исключений, включая миниатюры.
3. **Удаление пользователем и удаление аккаунта физически стирают объекты**,
   а не только строки.
4. Гостевые загрузки переезжают в аккаунт при склейке — вместе с генерациями.

### Что переезжает, а что остаётся в Redis

| Ключ сейчас | Куда |
| --- | --- |
| `user:email:*`, `user:apple:*`, `user:boostify:*` | `users` + `auth_identities` |
| `generation:{id}`, `user:generations:{uid}` | `generations` |
| `chat:{id}`, `user:chats:{uid}` | `chats`, `chat_messages` |
| `share:{share_id}` | колонка `generations.share_id` |
| `teki_balance` (поле пользователя) | `wallet_balances` + `wallet_ledger` |
| `session:{sid}` | остаётся в Redis |
| `magic:{token}`, `reset:{token}` | остаётся в Redis (TTL — родная механика) |
| rate limits, локи, кэш каталога | остаётся в Redis |

### Что это меняет в эскизе из прошлой версии

- `daily_rewards` схлопнут в `wallet_balances`;
- добавлен `appstore_notifications` — дедуп доставки уведомлений оказался проще
  и надёжнее как таблица, чем как логика;
- у генераций появилось мягкое удаление, потому что жёсткое ломает журнал;
- `avatar_key` и `result_key` хранят **ключи объектов**, а не URL: иначе смена
  провайдера хранилища или подключение CDN превращаются в миграцию данных.

## 2а. Эскиз (историческая версия, для сверки)

**Личность**

- `users` — `id`, `kind` (`guest` | `registered`), `email`, `name`, `avatar_key`,
  `created_at`, `deleted_at`, `merged_into_user_id`.
  Гость — строка в той же таблице, а не отдельный механизм.
- `auth_identities` — `user_id`, `provider` (`email`/`apple`/`google`),
  `external_id`, уникальность по паре (provider, external_id).
  Позволяет привязать к одному аккаунту несколько способов входа.

**Кошелёк**

- `wallet_balances` — `user_id`, `free_balance`, `sub_balance`,
  `sub_period_started_at`, `sub_period_ends_at`, `free_cap`.
  Две корзины отдельными полями — это прямое следствие решения из CH-17.
- `wallet_ledger` — **append-only** журнал: `id`, `user_id`, `bucket`
  (`free`/`sub`), `delta`, `reason` (`signup`, `daily_reward`, `sub_grant`,
  `sub_reset`, `generation`, `refund`), `ref_id`, `idempotency_key` (уникальный),
  `created_at`.
  Баланс = материализованная сумма журнала. Любую жалобу можно разобрать,
  любую операцию — повторить безопасно.
- `daily_rewards` — `user_id`, `last_claim_date`, `streak`. Дата — **серверная**,
  иначе перевод часов на устройстве превращается в бесконечные награды.

**Подписка**

- `subscriptions` — `user_id`, `original_transaction_id` (**уникальный**),
  `product_id`, `status` (`active`/`grace`/`expired`/`refunded`),
  `current_period_start/end`, `environment` (sandbox/production),
  `last_notification_at`, `raw_payload`.
  Уникальность `original_transaction_id` — то, что не даёт одной покупке
  начислить квоту дважды и двум аккаунтам делить одну подписку.

**Контент**

- `styles` — `id`, `title`, `description`, `type` (image/video), `needs_photo`,
  `cost`, `prompt_template` (jsonb), `examples` (jsonb), `sort_order`,
  `is_home`, `is_shot`, `is_active`, `usage_count`.
  Ручная курация — это `sort_order` + `is_home`; `usage_count` пишем с первого
  дня, даже пока не используем.
- `generations` — `id`, `user_id`, `style_id`, `type`, `status`, `prompt`,
  `request_params` (jsonb — то, чего сейчас не хватает для «повторить»),
  `result_key`, `thumb_key`, `cost`, `chat_id`, `share_id`, `created_at`,
  `deleted_at` (мягкое удаление, чтобы «удалить» не ломало журнал списаний).
- `chats`, `chat_messages` — как сейчас, но в таблицах.

**Индексы, без которых экран истории будет тормозить:**
`generations (user_id, created_at desc)` и `generations (user_id, type, created_at desc)`.

## 3. Безопасность

Приоритет — деньги и персональные данные, остальное вторично.

1. **Баланс никогда не приходит от клиента.** Клиент показывает то, что отдал
   сервер; списание считает только сервер.
2. **Идемпотентность на всех начислениях.** Уведомление App Store может прийти
   дважды, сеть может повторить запрос. Ключ идемпотентности в журнале делает
   повтор безвредным.
3. **Проверка подписки только на сервере**: App Store Server API + Server
   Notifications v2 с проверкой подписи JWS. Локальный чек в приложении —
   не доказательство.
4. **Списание и генерация — одна транзакция по смыслу.** Сейчас это две фазы
   (reserve → confirm/cancel), и логика уже умеет откатывать; в Postgres это
   становится честным, а не «на честном слове».
5. **Склейка гостя с аккаунтом — в одной транзакции.** Иначе прерванный перенос
   оставит генерации без владельца или удвоит баланс.
6. **Файлы приватны по умолчанию.** Бакет закрыт, доступ — по временной
   подписанной ссылке (5–15 минут), которую выдаёт API после проверки прав.
   Публичным остаётся только то, что пользователь явно расшарил.
7. **Удаление аккаунта — анонимизация, а не `DELETE FROM users`.** Журнал
   операций ссылается на пользователя внешним ключом и физически не даёт стереть
   строку — это проверено на живой схеме, и это правильно: бухгалтерия не должна
   исчезать вместе с человеком. Удаление означает: снять email, имя, аватар,
   **физически стереть объекты из хранилища**, проставить `deleted_at`, погасить
   сессии и расшаренные ссылки. Идентификатор остаётся в журнале, но никого
   больше не идентифицирует.
8. **Референсные фото — самые чувствительные данные в системе** (лица).
   Для них стоит отдельный срок хранения: они нужны только на время генерации.

## 4. Файловое хранилище

### Что нужно

Абстракция `app/storage/` с двумя реализациями: локальная папка (разработка) и
S3-совместимая (прод). Код генерации не должен знать, куда пишет, — сейчас
`Path("uploads").write_bytes(...)` раскидан по `video_gen.py` и `generate.py`.

Хранилище приватное; наружу отдаются **подписанные ссылки** через API, а не
прямые пути. В базе хранится ключ объекта (`result_key`), а не URL, — иначе
переезд между провайдерами превратится в миграцию данных.

### Сколько это будет стоить

Оценка при бессрочном хранении. Цифры — прикидка по типичным размерам,
уточнятся на реальных данных.

Допущения: изображение (PNG 1024×1024) ≈ 2 МБ, превью ≈ 60 КБ, видео 720p/5 с
≈ 6 МБ, референсное фото ≈ 2 МБ; 80% генераций — изображения, 20% — видео.

| Активных в день | Генераций/день | Прирост в день | В месяц | За год |
| --- | --- | --- | --- | --- |
| 100 | 300 | ~1 ГБ | ~30 ГБ | ~0.4 ТБ |
| 1 000 | 3 000 | ~10 ГБ | ~300 ГБ | ~3.6 ТБ |
| 10 000 | 30 000 | ~100 ГБ | ~3 ТБ | ~36 ТБ |

Ключевой расход при мобильном приложении — **не хранение, а исходящий трафик**:
каждый файл скачивается по нескольку раз (сетка, просмотр, сохранение).
При 1 000 активных это порядка 900 ГБ/месяц исходящего.

| Вариант | Хранение | Исходящий трафик | Комментарий |
| --- | --- | --- | --- |
| **MinIO в своём кластере** | цена дисков | внутри своего канала | команда уже эксплуатирует MinIO в соседнем проекте; нужен PVC и бэкапы |
| **Cloudflare R2** | ~$0.015/ГБ·мес | **$0** | egress бесплатный — при медиа-приложении это решающий пункт |
| **AWS S3** | ~$0.023/ГБ·мес | ~$0.09/ГБ | ~$80/мес трафика уже на 1 000 активных |

**Рекомендация:** сделать абстракцию сейчас, стартовать на MinIO в кластере
(инфраструктура своя, опыт есть), а R2 держать как запасной вариант, если
исходящий трафик станет заметной статьёй. Переезд при наличии абстракции —
это конфиг и перенос объектов, а не переписывание кода.

### CDN — решено подключать позже

Отложено сознательно, но два требования появляются **уже сейчас**, иначе позже
придётся переделывать:

1. **В базе хранится ключ объекта, а не URL.** Тогда включение CDN — это смена
   способа выдачи ссылки, а не миграция данных. Это уже заложено в схему
   (`result_key`, `thumb_key`, `avatar_key`).
2. **CDN не должен отменить приватность.** Классическая ошибка: файлы делают
   публичными «чтобы CDN мог их кэшировать», и починенная дыра открывается
   заново. Правильный вариант — подписанные ссылки, которые проверяются на
   краю (CloudFront signed URLs, Cloudflare signed URLs у R2). Отсюда практический
   вывод: если CDN в планах, **R2 + Cloudflare выглядит цельнее**, чем MinIO,
   к которому CDN придётся приделывать отдельно.

Что кэшируется хорошо: миниатюры и примеры стилей — они одинаковы для всех.
Персональные результаты кэшируются плохо по своей природе (у каждого свои),
поэтому основной выигрыш CDN здесь — витрина, а не история.

Отдельно: миниатюры обязательны (CH-13). Генерировать при сохранении, хранить
рядом, отдавать в сетку историю только их.

## Решено

1. **PostgreSQL добавляем** — SQLAlchemy 2.0 async + asyncpg + Alembic, слой
   репозиториев между роутерами и таблицами.
2. **Обрезку истории до 200 записей и публичный `/uploads` — чиним.**
3. **CDN подключаем позже**, но ключи объектов и подписанные ссылки закладываем
   сразу, чтобы включение CDN не потребовало переделки.
4. **Объектное хранилище — MinIO** в своём кластере. Что к нему прилагается:
   постоянный том, бэкапы (потеря бакета = потеря всех работ пользователей),
   политика жизненного цикла и отдельный бакет под окружение. CDN, когда дойдёт
   очередь, ставится перед MinIO отдельным слоем — и **обязан сохранить
   подписанные ссылки**, иначе публичность вернётся через заднюю дверь.
5. **Старые данные не переносим** — разработка MVP только стартует, база
   заводится чистой. Следствие, которое стоит проговорить: аккаунты, генерации
   и балансы, которые сейчас живут в Redis на `193.149.190.155`, после переезда
   не существуют. Если там есть хоть один живой пользователь или демо-аккаунт
   для показов — их надо будет завести заново.
6. **Референсные фото хранятся бессрочно и привязаны к аккаунту**, вместе с
   результатами образуя единую библиотеку медиа (`media_assets`). В будущем
   выбор референса — это галерея внутри приложения, где вперемешку загрузки и
   сгенерированное; см. CH-18 в [CHANGES-DRAFT.md](CHANGES-DRAFT.md).

7. **Аналитика — PostHog**, своя база событий не заводится: таблицы `events`
   в схеме нет, `/api/events` остаётся техническим каналом без хранения.
8. **Генерация из фото — блокер №1**, спайк по модели идёт раньше каталога.
   Старый каталог (29 плиток) в архив, новый пишется под выбранную модель.

корзины) и правила на их основе — порядок сгорания уже описан, значения нет.
