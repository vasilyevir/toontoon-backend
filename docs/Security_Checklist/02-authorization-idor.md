## 1. IDOR / Broken Object Level Authorization

| # | Проверка | Крит. | Что искать / вектор | Как исправить |
|---|----------|-------|---------------------|---------------|
| AZ-1.1 | Фильтрация по владельцу | 🔴 | `Model.objects.get(id=request_id)` без `user=request.user`. `/api/users/123/earnings` → `456` | Все queryset фильтровать по `request.user` |
| AZ-1.2 | Проверка на write | 🔴 | Может ли A изменить/удалить объект B, подменив ID | Проверять владение перед изменением |
| AZ-1.3 | Вложенные ресурсы | 🟠 | `/orders/{myOrder}/items/{notMyItem}` | Проверять всю цепочку принадлежности |
| AZ-1.4 | IDOR в merchant/tenant API | 🟠 | Фильтр по `g.merchant.id` пропущен на части эндпоинтов | Единый tenant-scoped queryset |
| AZ-1.5 | IDOR через batch/bulk | 🟠 | Массовые операции по списку ID без проверки каждого | Валидировать владение каждым элементом |
| AZ-1.6 | IDOR в файлах/медиа | 🟠 | Прямой доступ по предсказуемому пути/ID | Проверка прав перед выдачей + непубличное хранение |

> ⚠️ **IDOR — самый частый и самый недооценённый класс.** Проверяй **каждый** эндпоинт, который
> принимает ID объекта: подставь чужой ID под своей сессией. Если вернулись чужие данные — Critical
> при финансах/PII.

## 2. Mass Assignment / Over-posting

| # | Проверка | Крит. | Что искать / вектор | Как исправить |
|---|----------|-------|---------------------|---------------|
| AZ-2.1 | Whitelist полей сериализатора | 🔴 | Клиент шлёт `is_staff`, `role`, `balance`, `is_verified` | Явный `fields` / `read_only_fields`, не `__all__` |
| AZ-2.2 | Защита финансовых полей | 🔴 | Можно передать `amount`, `discount`, `price` в update | Серверная установка, read-only на клиенте |
| AZ-2.3 | Вложенные объекты | 🟠 | Обновление связанной модели через nested serializer | Явно контролировать writable nested |
| AZ-2.4 | ORM `update()`/`**kwargs` | 🟠 | `Model.objects.filter().update(**request.data)` | Явный список разрешённых полей |
| AZ-2.5 | `setattr` из request | 🟠 | `for k,v in data.items(): setattr(obj,k,v)` | Whitelist ключей |

## 3. RBAC и разделение ролей

| # | Проверка | Крит. | Что искать / вектор | Как исправить |
|---|----------|-------|---------------------|---------------|
| AZ-3.1 | Разделение ролей | 🟠 | Support/Leader/Admin/Superuser имеют одинаковые права | Явные группы с минимальными полномочиями |
| AZ-3.2 | Проверка прав на каждом эндпоинте | 🟠 | Часть admin-роутов без permission class | `@require_role(...)` на каждом |
| AZ-3.3 | Double-enforcement | 🟡 | Права проверяются только в UI (скрытие кнопки) | И в UI, и в backend (внутри действия) |
| AZ-3.4 | Явный deny, не allowlist+redirect | 🟡 | «Не в allowlist → redirect» (легко забыть новый роут) | Явные декораторы ролей, `403` а не redirect |
| AZ-3.5 | Fail-closed по умолчанию | 🟠 | Новый эндпоинт по умолчанию открыт | Default deny; доступ добавляется явно |
| AZ-3.6 | Staff-права на фин. моделях | 🟠 | `has_delete/change_permission` для Purchase/Earning | Блокировать изменение/удаление фин. записей |
| AZ-3.7 | Confirmation workflow | 🟡 | Необратимые операции без preview→confirm | Двухшаговое подтверждение |

## 4. Эскалация привилегий

| # | Проверка | Крит. | Что искать / вектор | Как исправить |
|---|----------|-------|---------------------|---------------|
| AZ-4.1 | Горизонтальная (H-priv) | 🟠 | Обычный юзер дёргает admin/support URL напрямую | Permission class на каждом роуте |
| AZ-4.2 | Вертикальная (V-priv) | 🟠 | Support выполняет действия superuser | Проверять конкретное право, не «залогинен» |
| AZ-4.3 | Смена роли через профиль | 🔴 | `POST /users/{id}/roles` без RBAC-проверки | Только привилегированные могут менять роли |
| AZ-4.4 | Privilege через mass assignment | 🔴 | `role=admin` в update профиля | См. AZ-2.1 |
| AZ-4.5 | `basic_auth_optional` на деньгах | 🟠 | Опциональная basic-auth принимает любого юзера | Один явный механизм auth на фин. эндпоинтах |
| AZ-4.6 | JWT `is_staff`/`role` из клиента | 🔴 | Роль берётся из claim без сверки с БД | Роль из БД по user_id |

> ⚠️ **Урок из практики:** `POST /api/users/{id}/roles` без RBAC-проверки — потенциальный privesc.
> Любое изменение ролей/прав — только для явно уполномоченных, с audit-логом.

## Быстрые команды проверки

```bash
# IDOR: get/filter по id без привязки к пользователю
rg "\.objects\.get\(.*\bid=" --type py | rg -v "request\.user|user=|owner="
rg "\.objects\.filter\(.*\bpk=" --type py | rg -v "request\.user"

# Mass assignment: сериализаторы без read_only_fields / с __all__
rg "fields\s*=\s*['\"]__all__['\"]" --type py
rg "class.*Serializer" -A8 --type py | rg -L "read_only_fields"

# setattr из request
rg "setattr\(.*request\.(data|POST)" --type py

# Роуты без permission
rg "@(app|router|bp)\.(get|post|put|delete|patch)" -A3 --type py | rg -L "permission|require_role|login_required"
```

Тестовый сценарий IDOR (ручной): залогинься как user A, сохрани cookie/token, обратись к ресурсам
user B, подставляя его ID во все эндпоинты. Любой успешный ответ с чужими данными — находка.
