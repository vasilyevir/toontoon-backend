# 25 — Incident Response

## 1. Немедленные действия (0–1 час)

| # | Действие | Ответственный | Статус |
|---|----------|---------------|--------|
| IR-1.1 | Определить scope: что скомпрометировано, какие данные затронуты | Security Lead | [ ] |
| IR-1.2 | Остановить активную атаку: заблокировать IP, отключить эндпоинт (на прокси — быстро) | DevOps | [ ] |
| IR-1.3 | Сохранить forensic evidence: логи, дампы памяти, трафик (до очистки!) | DevOps | [ ] |
| IR-1.4 | Уведомить core team: CTO, Security Lead, Team Leads | Security Lead | [ ] |
| IR-1.5 | Начать timeline инцидента (кто/что/когда) | Security Lead | [ ] |

## 2. Containment (1–4 часа)

| # | Действие | Описание |
|---|----------|----------|
| IR-2.1 | Ротация скомпрометированных ключей | Signer keys, API keys, JWT secret, DB passwords — всё, что могло утечь |
| IR-2.2 | Инвалидация всех сессий/JWT | Смена `SECRET_KEY` → все токены невалидны |
| IR-2.3 | Заморозка выводов | `pause()` на контракте / отключение claim-эндпоинтов |
| IR-2.4 | Блокировка подозрительных аккаунтов | `is_active=False` для участников атаки |
| IR-2.5 | Snapshot состояния БД | Полный дамп для расследования |
| IR-2.6 | Быстрый митигейт на периметре | Блок путей/CORS/rate-limit на reverse-proxy без передеплоя |

---

## 3. Расследование (4–48 часов)

| # | Действие | Описание |
|---|----------|----------|
| IR-3.1 | Timeline атаки | Первый вход, действия, объём ущерба |
| IR-3.2 | Root cause analysis | Какая уязвимость эксплуатирована |
| IR-3.3 | Blast radius | Какие данные/средства/пользователи затронуты |
| IR-3.4 | Проверка на persistence | Бэкдоры, новые аккаунты, cron/systemd, SSH-ключи, реверс-шеллы |
| IR-3.5 | Анализ логов доступа | Был ли доступ к инфраструктуре (SSH, auditd, access-логи) |
| IR-3.6 | Проверка целостности | Изменённые файлы, `authorized_keys`, новые порты |

> 💡 **Что проверять на persistence:** новые слушающие порты (`ss -tulpn`), изменения
> `~/.ssh/authorized_keys`, чужие cron/systemd-юниты, реверс-шеллы (`nc`/`socat`/`/tmp/*`), успешные
> SSH-входы (по ключу владельца или нет), fail2ban-баны, access-логи прокси на `/.env`/`/.git`.

## 4. Recovery и Post-mortem

| # | Действие | Описание |
|---|----------|----------|
| IR-4.1 | Устранение уязвимости | Patch + code review + deploy |
| IR-4.2 | Восстановление сервиса | Поэтапно: сначала read-only, потом полный доступ |
| IR-4.3 | Уведомление пострадавших | При затронутых данных/средствах — notification (учесть 72ч GDPR) |
| IR-4.4 | Post-mortem документ | Что случилось, почему, что сделали, как предотвратить (blameless) |
| IR-4.5 | Обновление чеклиста | Добавить новые проверки на основе инцидента |
| IR-4.6 | Свёртывание временного мониторинга | Убрать IR-инструменты, оставить боевую защиту (SSH-hardening, fail2ban, updates) |

## 5. Чек-лист безопасной выкатки фикса

Для каждого изменения, затрагивающего деньги/ключи/приём платежей (🟥):

- [ ] Объявлено maintenance-окно, деплои заморожены
- [ ] Зафиксировано «зелёное» состояние: healthcheck'и зелёные
- [ ] Бэкап БД (все схемы) + том/volume приложения
- [ ] Бэкап `.env` и текущего кода (git commit/tag)
- [ ] Применено **РОВНО ОДНО** изменение
- [ ] Перезапущен минимально необходимый сервис
- [ ] Smoke-тест canary: инвойс → входящая tx → вебхук получен
- [ ] Smoke-тест малой выплаты на canary-сети
- [ ] Логи чисты 10–15 мин (нет ошибок ключа/расшифровки/БД)
- [ ] Раскатано на остальное ИЛИ выполнен откат
- [ ] Статус обновлён в трекере

### Шаблон бэкапа (пример)

```bash
# БД (шифрованно — там могут быть ключи/PII):
docker exec <db> sh -c 'exec mariadb-dump -uroot -p"$MARIADB_ROOT_PASSWORD" --all-databases' \
  | gzip | age -r <recipient> > backup_$(date +%F).sql.gz.age

# Volume приложения:
docker run --rm -v <app_volume>:/data -v "$PWD":/out alpine \
  sh -c 'cd /data && tar czf /out/app_$(date +%F).tar.gz .'
```

> 💡 Многие Critical/High закрываются **без передеплоя** на reverse-proxy (блок путей, CORS,
> заголовки, rate-limit) — это первая линия containment. См. [19](./19-infrastructure-docker-k8s.md) §3.
