## 1. Порядок аудита

Рекомендуемая последовательность (от самого «денежного» риска к периферии):

1. **Разведка** — структура проекта, стек, зависимости, документация, точки входа.
2. **Секреты** — `.env`, git-история, захардкоженные ключи, deploy-конфиги → [04](./04-secrets-management.md).
3. **Аутентификация** — все точки входа, OAuth, кошельки, JWT, сессии → [01](./01-authentication.md), [03](./03-session-management.md).
4. **Финансовые потоки** — платежи, подписи, вебхуки, выводы, комиссии → [13](./13-payments-webhooks.md)–[16](./16-referral-commission.md).
5. **Авторизация** — RBAC, IDOR, привилегированные эндпоинты → [02](./02-authorization-idor.md).
6. **Входные данные** — валидация, инъекции, SSRF, upload → [05](./05-injections.md), [06](./06-input-validation.md), [11](./11-ssrf.md), [12](./12-file-upload.md).
7. **Бизнес-логика** — state machine, TOCTOU, workflow bypass → [17](./17-business-logic.md).
8. **Фронтенд** — токены, CSP, CORS, XSS, третьи стороны → [07](./07-xss.md), [08](./08-csrf-cors-headers.md), [10](./10-frontend-config.md).
9. **Инфраструктура** — Docker, K8s, cloud, CI/CD, сеть → [19](./19-infrastructure-docker-k8s.md), [20](./20-cloud-security.md).
10. **Наблюдаемость** — логи, мониторинг, обработка ошибок → [22](./22-logging-monitoring.md), [23](./23-error-handling.md).

## 2. Определение Scope

| # | Проверка | Критичность | Что зафиксировать |
|---|----------|-------------|-------------------|
| SCOPE-1 | Что **в скоупе** | — | Backend / frontend / infra / smart-contract interaction / mobile |
| SCOPE-2 | Что **вне скоупа** | — | Мобильные клиенты, on-chain контракты, третьи стороны, соседние сервисы |
| SCOPE-3 | Версии/коммиты | — | Точные git-хэши / теги аудитируемого кода |
| SCOPE-4 | Уровень доступа аудитора | — | white-box (код) / gray-box (частичный) / black-box (снаружи) |
| SCOPE-5 | Тип работ | — | Неразрушающий аудит / активная эксплуатация / DAST на staging |
| SCOPE-6 | Границы окружений | — | prod / staging / dev — где что можно проверять |
| SCOPE-7 | Юридическое разрешение | 🔴 | Письменное разрешение на тестирование (rules of engagement) |
| SCOPE-8 | Assets под защитой | — | Средства пользователей, приватные ключи, PII, репутация, доступность |

> ⚠️ **Урок из практики:** соседний сервис на другой инфраструктуре имел критичные находки,
> но был **вне scope** — их фиксируют для передачи ответственной команде, а не молча тестируют.

## 3. Разведка (Reconnaissance)

| # | Проверка | Что искать |
|---|----------|-----------|
| RECON-1 | Стек технологий | Языки, фреймворки, БД, брокеры, blockchain-сети |
| RECON-2 | Карта эндпоинтов | Все роуты, включая скрытые (`include_in_schema=False`) |
| RECON-3 | Точки входа | HTTP API, вебхуки, WebSocket, GraphQL, admin-панель, CLI, cron |
| RECON-4 | Внешние домены | Каждый vhost и что он проксирует (см. reverse-proxy конфиг) |
| RECON-5 | Trust boundaries | Клиент↔API, API↔blockchain, API↔payment provider, API↔внутр. сеть |
| RECON-6 | Data flow diagram | Как движутся деньги, PII, ключи через систему |
| RECON-7 | Зависимости | `requirements.txt`, `package.json`, lock-файлы, образы контейнеров |
| RECON-8 | Документация | README, ADR, комментарии `TODO/FIXME/hack/bypass/temporarily` |

### Карта доверия — шаблон

```
Интернет ─► Reverse Proxy (TLS) ─► App
   │                                 ├─► DB (секреты/PII/ключи)   [внутр.]
   │                                 ├─► Cache/Broker (Redis)     [внутр.]
   │                                 └─► внешние API/RPC/провайдеры
   │
   └─(тот же домен?)─► /internal/*, /webhook/*, /admin/*  ⚠ должны быть закрыты снаружи
Мерчант ◄── вебхук (callback_url задаётся клиентом) ◄── App   ⚠ SSRF-вектор
```

## 4. Threat Modeling (STRIDE)

Для каждого ключевого компонента пройди 6 категорий угроз STRIDE:

| Буква | Угроза | Вопрос | Контрмера |
|-------|--------|--------|-----------|
| **S** | Spoofing (подмена) | Можно ли выдать себя за другого? | Аутентификация, подписи, mTLS |
| **T** | Tampering (изменение) | Можно ли подменить данные в транзите/хранении? | HMAC, целостность, `select_for_update` |
| **R** | Repudiation (отказ) | Можно ли отрицать действие? | Audit log с before/after |
| **I** | Information Disclosure | Что утекает? | Шифрование, redaction логов, 404 vs 403 |
| **D** | Denial of Service | Можно ли положить сервис? | Rate limiting, лимиты ресурсов, таймауты |
| **E** | Elevation of Privilege | Можно ли поднять права? | RBAC, проверка на каждом эндпоинте |

### Attack Trees

Для ключевых сценариев (кража средств, account takeover, утечка ключей) построй дерево атак:
корень = цель атакующего, ветви = пути достижения. Помогает найти неочевидные цепочки.

> **Пример цепочки:** дефолтный backend-key → доступ к служебному эндпоинту из интернета →
> получение ключа шифрования → дамп БД → расшифровка всех приватных ключей → полный вывод средств.
> Три «Medium» находки в сумме дают **Critical**.

## 5. Severity Scoring и приоритизация

| # | Правило | Детали |
|---|---------|--------|
| SEV-1 | Привязка к CVSS 3.1/4.0 | Базовый вектор для объективности |
| SEV-2 | Контекст бизнеса | CVSS Medium на финансовой операции = фактически High/Critical |
| SEV-3 | Формула приоритета | `Priority = Severity × Exploitability × Business Impact` |
| SEV-4 | Ближе к деньгам — раньше | При равной критичности сначала деньги/ключи/PII |
| SEV-5 | Учёт цепочек | Связанные Medium-находки могут давать Critical в сумме |
| SEV-6 | Учёт компенсирующих контролей | Есть ли WAF/сегментация/мониторинг, снижающие реальный риск |

### Шкала критичности (единая для всех файлов)

| Значок | Уровень | SLA |
|--------|---------|-----|
| 🔴 | Critical — кража средств/RCE/утечка ключей | 0–24 ч |
| 🟠 | High — цепочка атак/крупная утечка/обход auth | 1–7 дней |
| 🟡 | Medium — ослабление защиты/info disclosure | 2–4 недели |
| 🟢 | Low — best practice | При случае |
| ⚪ | Info — гигиена/наблюдение | Бэклог |

## 6. Что искать в первую очередь

Быстрые индикаторы проблем (см. команды в [27](./27-quick-commands.md)):

- Скрытые/недокументированные эндпоинты (`include_in_schema=False`, закомментированные роуты).
- Комментарии: `temporarily`, `TODO`, `FIXME`, `hack`, `bypass`, `no validation`, `disable`.
- Отключённые проверки: `verify=False`, `check=False`, `validate=False`, `verify_signature: False`.
- Разница закомментированного старого и нового кода — **не убрали ли защиту?**
- Финансовые эндпоинты с `auth=None`, `permissions=[AllowAny]`, `@basic_auth_optional`.
- Дефолтные секреты: `dev`, `password123!`, `changeme`, `admin`, `test`.
- `return` вместо `raise` в проверке подписи/прав (не прерывает выполнение).
- Клиент передаёт то, что должен определять сервер: цену, скидку, сумму, `is_staff`, `role`.

## 7. Re-test и Sign-off

| # | Шаг | Описание |
|---|-----|----------|
| RETEST-1 | Fix verification | Повторная проверка конкретной находки после фикса |
| RETEST-2 | Regression check | Fix не сломал смежную функциональность |
| RETEST-3 | Sign-off | Аудитор подтверждает закрытие с датой и коммитом |
| RETEST-4 | Periodic re-audit | Полный повтор каждые 3–6 мес или после major release |
| RETEST-5 | Обновление чеклиста | Новые проверки на основе найденного инцидента |

## 8. Правило «не сломать прод»

Для каждой находки, затрагивающей денежный поток / ключи / приём платежей (пометка 🟥):

1. **Бэкап** БД + `.env` + git tag текущего состояния.
2. **Staging** — воспроизведение фикса на копии.
3. **Canary** — выкатка на одну сеть/сегмент, наблюдение логов 10–15 мин.
4. **Rollout** — полная выкатка или **откат** по заранее готовому плану.
5. Только в **maintenance-окне**, по **одному изменению** за раз.

> 💡 **Приоритет быстрого митигейта:** многие Critical/High закрываются на reverse-proxy (Caddy/nginx)
> **без передеплоя приложения** — блокировкой служебных путей снаружи, CORS, security-заголовками,
> rate-limit через fail2ban поверх access-логов. Внутренние демоны ходят к приложению по внутренней
> сети мимо прокси, поэтому внешний deny их не ломает. Используй это как первую линию.

Чек-лист безопасной выкатки — в [25 — Incident Response](./25-incident-response.md) и [19 — Инфраструктура](./19-infrastructure-docker-k8s.md).
