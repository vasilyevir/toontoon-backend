# Логин/регистрация: Email + пароль — как сделать правильно

План под наш стек (FastAPI + Redis, SwiftUI-апка, HTTPS с пиннингом уже есть).
Способ: классические регистрация и вход по email+паролю, сессия — токеном в JSON
(для мобилки), cookie оставляем для веба.

---

## 0. Почему подходит именно нам
- ✅ **Работает сразу, без почтового сервиса и без домена** — регистрация и вход
  ничего не отправляют. (У OTP/magic-link это блокер, у нас домена пока нет.)
- ✅ HTTPS уже настроен → пароли не ходят открытым текстом.
- ⚠️ **«Забыли пароль» всё равно потребует почту** — но это отдельный шаг, его
  можно отложить (или временно сбрасывать вручную) до появления домена/почты.
- ⚠️ Без верификации email возможны «левые» адреса — на старте допустимо, позже
  добавим подтверждение письмом.

---

## 1. Модель данных (что добавить)
В `app/models/user.py`:
- В `User` добавить `password_hash: Optional[str] = None`.
- В `AuthProvider` добавить значение `EMAIL = "email"` (наряду с magic/boostify).
- В Redis уже есть индекс `user:email:{email}` — используем его для поиска.

**Совместимость:** старые magic-пользователи без пароля просто не смогут войти
по паролю, пока не «установят» его (или мигрируем — на раннем этапе не критично).

## 2. Хеширование пароля (обязательно)
- Библиотека: **argon2-cffi** (`argon2id`, рекомендуется) или **bcrypt** (через
  `passlib[bcrypt]`). Добавить в `requirements.txt`.
- Хранить **только хеш** (`password_hash`), с солью (встроена в argon2/bcrypt).
- Проверка — встроенная verify (постоянное время). Никогда не логировать пароль.

## 3. Правила пароля и валидация
- Мин. длина **8** символов (лучше 10+), максимум ~128.
- Не запрещать спецсимволы; проверять на «слишком простой» — опционально.
- На клиенте — базовая проверка (длина, совпадение с «повтор пароля»);
  на сервере — авторитетная проверка.
- Email нормализовать (lowercase, trim), валидировать (`EmailStr` уже есть).

## 4. Эндпоинты (доработка бэкенда)
Все под `/api/auth`, тело JSON, ответ — **и cookie, и session token в JSON**
(мобилка берёт токен, веб — cookie).

### 4.1 Регистрация
```
POST /api/auth/register
{ "email": "...", "password": "...", "name": "..."? }
→ 201 { "user": PublicUser, "session_token": "<sid>" }
Ошибки: 409 email_taken, 422 weak_password / bad_email
```
Логика: нормализовать email → проверить, что нет `user:email:{email}` →
хешировать пароль → создать `User` (provider=email, стартовый TEKI-баланс) →
создать сессию → вернуть токен + поставить cookie.

### 4.2 Вход
```
POST /api/auth/login
{ "email": "...", "password": "..." }
→ 200 { "user": PublicUser, "session_token": "<sid>" }
Ошибки: 401 invalid_credentials (единый текст — не раскрывать, есть ли email)
```
Логика: найти user по email → `verify(password, hash)` → создать сессию → токен.

### 4.3 Уже есть (переиспользуем)
- `GET /api/auth/me` — текущий пользователь.
- `DELETE /api/auth/me` — logout (удаляет сессию).
- `PATCH /api/auth/profile` — имя/аватар.

### 4.4 Позже (нужна почта)
- `POST /api/auth/password/forgot {email}` — выслать ссылку/код сброса.
- `POST /api/auth/password/reset {token, new_password}`.
- `POST /api/auth/email/verify` — подтверждение email.

## 5. Защита от брутфорса (обязательно)
- Rate limit на `/login` **по email и по IP** (в проекте уже есть
  `core/rate_limit.py`): напр. 5–10 попыток / 15 мин, затем временная блокировка.
- Единый ответ `invalid_credentials` (не различать «нет email» / «неверный пароль»).
- Небольшая задержка/константное время на неуспехе (argon2 сам небыстрый — ок).
- Rate limit и на `/register` (против массового создания аккаунтов).

## 6. Приложение (SwiftUI) — что сделать
- **Экран входа**: email + пароль + кнопка «Войти» + ссылка «Создать аккаунт».
- **Экран регистрации**: email + пароль (+ «повторите пароль») + имя (опц.) +
  кнопка «Зарегистрироваться».
- Клиентская валидация: формат email, длина пароля, совпадение паролей.
- Показ ошибок: 409 (email занят), 401 (неверные данные), 422 (слабый пароль).
- Хранить `session_token` в **Keychain** (механизм уже есть в `AuthManager`/`KeychainStore`).
- Все запросы уже идут по HTTPS с пиннингом (`APISecurity`).
- Поле пароля — `SecureField`, автозаполнение паролей iOS (`textContentType`).
- (Позже) «Забыли пароль».

> Отличие от текущего кода: сейчас в апке `AuthManager` реализует magic-link +
> перехват cookie. Для email+пароля добавляем методы `register`/`login`, которые
> берут `session_token` прямо из JSON (проще, без перехвата редиректа).

## 7. Безопасность (чек)
- ✅ HTTPS + пиннинг уже есть (пароли не в открытом виде).
- ✅ Хеш argon2/bcrypt, соль, verify в постоянное время.
- ✅ Rate limit + единый текст ошибки.
- ✅ Пароль только в `SecureField`, не логируется, не кэшируется.
- ⚠️ Перед публичным релизом — подтверждение email + сброс пароля (нужна почта).

## 9. Решения, которые нужны от тебя

2. **Мин. длина пароля** — 8 или строже?
3. **«Повторите пароль»** на экране регистрации — нужен?
4. **Верификация email** сейчас (нужна почта) или отложить до домена?
5. **Веб-фронт**: оставляем как есть (magic-link) или тоже переводим на пароль?
6. Разрешаешь ли аккуратно **править сервер** (добавить 2 эндпоинта), или сначала
   только клиент + спецификация для второго Claude?
