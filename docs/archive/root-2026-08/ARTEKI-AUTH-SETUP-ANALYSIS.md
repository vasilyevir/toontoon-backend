# Логин и регистрация — анализ и что нужно сделать

Документ-анализ (без изменений кода). Описывает, как вход/регистрация устроены
сейчас, какие есть пробелы, и что нужно, чтобы это по-настоящему работало в
мобильном приложении.

---

## 1. Как это устроено СЕЙЧАС (факты из кода)

- **Вход беспарольный (magic-link).** Пароля нет.
- **Регистрация = вход.** Один эндпоинт `POST /api/auth/magic-link`:
  `auth_service.get_or_create_magic_user(email)` — новый email → создаётся
  пользователь + стартовый баланс TEKI (**регистрация**); существующий → просто
  вход. Отдельной формы регистрации нет.
- **Письмо НЕ отправляется.** `POST /auth/magic-link` возвращает `devLink`
  (`/api/auth/verify?token=...`) прямо в JSON. В коде прямо помечено как
  временное решение до подключения реальной почты.
- **Экран «4 цифры» — косметика.** Бэкенд OTP не генерирует и не проверяет;
  подтверждение просто открывает `devLink`.
- **`verify` создаёт сессию** и ставит cookie `arteki-session` (TTL 30 дней),
  затем 302 на веб-фронт.
- **Boostyfi OAuth** (`/auth/boostify/login` → `callback`) реализован, но
  редиректит на веб (Трек B — под мобилку нужна доработка).
- **Google** — кнопка-заглушка «coming soon».

Хранилище (Redis): `user:{id}`, `user:email:{email}` (поиск по почте),
`session:{sid}`, `magic:{token}` (TTL 15 мин).

**Вывод:** текущий вход годится для разработки, но для реального приложения не
подходит — нет доставки письма/кода и нет проверки кода.

---

## 2. Что значит «настроить логин и регистрацию»
Нужно выбрать **реальный способ аутентификации** и довести его. Варианты ниже.

### Вариант A — Код на email (OTP, 4–6 цифр) ⭐ рекомендую
Пользователь вводит email → ему приходит **код** → вводит код → вход/регистрация.
Совпадает с уже нарисованным экраном ввода кода.

**Бэкенд (доработка):**
- Генерировать код (например 6 цифр), хранить в Redis `otp:{email}` с TTL ~10 мин
  и счётчиком попыток.
- **Отправлять код на email** через почтовый сервис (см. §4).
- Новый эндпоинт `POST /api/auth/otp/verify {email, code}` → проверка →
  `get_or_create_magic_user` → создать сессию → **вернуть session id в JSON**
  (для мобилки), а не только cookie-редирект.
- Ограничить частоту запросов кода (rate limit по email/IP).

**Приложение (доработка):**
- Экран email → `POST /auth/magic-link` (или новый `/auth/otp/request`).
- Экран кода → `POST /auth/otp/verify` → сохранить сессию в Keychain.
- Убрать «косметику» — код станет настоящим.

**Плюсы:** без паролей, знакомый UX, легко на мобиле. **Минусы:** нужен
почтовый сервис.

### Вариант B — Magic-link по email (ссылка)
Приходит письмо со **ссылкой**, тап открывает приложение (deep link) и логинит.
**Минусы:** сложнее на мобиле (нужен Universal Links / кастомная схема,
возврат в апку), письмо-ссылка. Для мобилки OTP-код (A) практичнее.

### Вариант C — Email + пароль (классика)
Регистрация с паролем, вход по паролю.
**Бэкенд:** хранить хеш пароля (bcrypt/argon2), эндпоинты `register`/`login`,
сброс пароля (всё равно нужна почта). **Больше кода и рисков** (утечки паролей),
поэтому для этого продукта менее предпочтительно.

### Вариант D — Sign in with Apple / Google (OAuth)
На iOS **Sign in with Apple почти обязателен**, если предлагаете сторонние
логины (правило App Store). Даёт быстрый вход без ввода email/кода.
**Бэкенд:** проверка Apple/Google id-token, создание пользователя, выдача сессии.
**Приложение:** `AuthenticationServices` (кнопка Apple).
Хорошо **в дополнение** к варианту A.

## 3. Рекомендация
1. **Основной способ — Вариант A (OTP-код на email).** Совпадает с текущим
   экраном, беспарольно, просто на мобиле.
2. **Добавить Sign in with Apple (часть D)** — нужен для публикации в App Store и
   ускоряет вход.
3. Boostyfi/Google (Трек B) — позже, когда понадобится Web3/соц-вход.

Регистрация при этом остаётся автоматической: первый вход по новому email
создаёт аккаунт (как сейчас), плюс можно на первом экране спросить имя.

---

## 4. Что понадобится ОТ ТЕБЯ (внешние сервисы/доступы)
- **Почтовый сервис для отправки кодов** — на выбор:
  - транзакционный API (Resend / Postmark / SendGrid / Mailgun / Amazon SES) —
    надёжнее всего, нужен API-ключ (хранить на сервере в `.env`);
  - или свой SMTP.
  - Нужен домен-отправитель (например `no-reply@arteki.ai`) + DNS-записи
    (SPF/DKIM), иначе письма уйдут в спам. **Домена пока нет** — это блокер для
    красивого адреса; на старте можно слать через сервис с их поддоменом.
- **Для Sign in with Apple:** аккаунт Apple Developer, Service ID, ключ (.p8),
  включённый capability в приложении.
- **(Опц.) Для Google:** OAuth client id/secret.

## 5. Что нужно доработать на сервере (сводка задач)
Для Варианта A:
- [ ] Хранение OTP в Redis (`otp:{email}`: код, попытки, TTL).
- [ ] Интеграция почтового сервиса (ключ в `.env`, функция `send_otp_email`).
- [ ] `POST /api/auth/otp/request {email}` — сгенерировать+отправить код (rate limit).
- [ ] `POST /api/auth/otp/verify {email, code}` — проверить → сессия → **session id в JSON**.
- [ ] Ограничения: TTL кода, лимит попыток, лимит запросов по email/IP.
- [ ] (Совместимость) оставить cookie-флоу для веба, но мобилке отдавать токен в теле.

Для части D (Apple):
- [ ] Эндпоинт `POST /api/auth/apple {identity_token}` — проверить подпись Apple → сессия.

## 6. Что нужно доработать в приложении (сводка задач)
- [ ] Экран email: запрос кода (`/auth/otp/request`).
- [ ] Экран кода: реальная проверка (`/auth/otp/verify`) → сессия в Keychain.
- [ ] Обработка ошибок: неверный код, истёк, лимит попыток, resend с кулдауном.
- [ ] (Опц.) Первый вход: спросить имя (`PATCH /auth/profile`).
- [ ] (Опц.) Кнопка Sign in with Apple (`AuthenticationServices`).
- [ ] Автовход при живой сессии (уже есть: cookie в Keychain + `GET /auth/me`).

## 7. Важные замечания
- **Сейчас безопасно только по HTTPS** (уже настроен, см. `SECURITY.md`) — коды
  и сессии не должны ходить по http.
- **Мобилке нужен токен в JSON**, а не редирект на веб — это ключевое отличие от
  текущего веб-флоу (см. `AUTH.md`, Трек B).
- **Регистрация не требует отдельного экрана** — она происходит при первом
  успешном вводе кода нового email. Если нужен явный шаг «создать аккаунт с
  именем» — это небольшой доп. экран.
- Оценка объёма Варианта A: бэкенд ~0.5–1 день (почта + 2 эндпоинта + лимиты),
  приложение ~0.5 дня (2 экрана + обработка ошибок). Apple-вход — ещё ~0.5–1 день.
